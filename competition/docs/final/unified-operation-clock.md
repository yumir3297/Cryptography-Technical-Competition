# 时钟故障：证据、处理与验证条件

本轮不修改 healthy、12.5 ms 的来源时钟差阈值、2 秒样本年龄、25 ms 余量、原窗口规则或冻结 Core。真实时钟不可确定仍须阻断。以下将已定位的自然故障与尚无法追溯的历史失败分开记录。

## 1. 已取得的自然故障证据

第一次统一联合运行中，C 子进程 pid 22366 在 2026-10-17 13:34:20（上海）实际生成 healthy=false 的样本：

- 起点至该样本：墙钟推进 70.527705000 秒；mach_absolute_time 单调计时推进 5.907297417 秒。
- 差值为 64.620407583 秒，远超过原允许阈值。
- 墙钟读取本身的单调包围跨度为 1,541 ns；读取墙钟后到原单调采样为 6,709 ns，不能用一次 12.5 ms 以上的调用间抢占解释该样本。
- 系统电源日志记载 13:33:13 因 Idle Sleep 进入休眠，13:34:19–20 因用户活动唤醒，与该异常一致。

运行时 get_clock_info 显示单调来源为 mach_absolute_time()，墙钟来源为 clock_gettime(CLOCK_REALTIME)。Apple 明确说明前者在系统睡眠期间不增加，见 [Apple mach_absolute_time 文档](https://developer.apple.com/documentation/kernel/1462446-mach_absolute_time)。这解释了本次经实测与系统日志互相印证的故障；不是签名失效、DENY 被错误拒绝或数据库重复接受。

本轮还经历了用户中断期间的后续自动休眠。运行不因观察超时被重启；原进程继续，相关失败保留在 joint-01。此运行不能当作稳定宿主条件下的最终验收，即使某些预期拒绝用例恰好捕获了自然时钟错误。

## 2. 最小工程处理

单机竞赛服务需使用运行期间不自动休眠的宿主。macOS 的验证入口 run_unified_checks.sh 使用 caffeinate -i <验证进程>，断言仅在该进程存活期间存在；不改变持久系统设置，不保持屏幕点亮，不修改任何签名/时钟判定。系统自带 caffeinate(8) 手册是这项运行条件的依据。

人工睡眠、合盖、电源中断、真实墙钟跳变仍可能发生；防空闲休眠不是新的可信时间证明。发生后保留原始样本和 W 状态，并返回 CLOCK_UNKNOWN／503。不得把已接受但回执待签改成未接受，也不得自动重新批准、重建 COMMIT 或重发 EXEC。

受控恢复先确认宿主可信时间状态，再重建原客户端/服务并连接原持久数据库；不调用初始化重置账。新的 C 实例仍受原签名、序列和持久时间 floor 验证；墙钟回退仍阻断。原依据、批准或 Permit 已过期则停止新接受，进入受控重新审批。已接受部分只恢复原冻结回执，工具未知只查询同一 attempt。无法恢复原回执有效窗口时保持待签，不重签新 Core。

## 3. 原始诊断与边界

diagnostic_runner 在测试清理前保存失败堆栈、已收到的签名样本、待签原因及公开 W/app/outbox/资源/消费状态。子进程诊断记录原 time_ns/monotonic_ns 返回值、取时跨度及原始起点；不调整返回值、不重签样本、不吞错重试。仅导出公开材料，不包含运行私钥或原始运行数据库。

注入的过期、2.01 秒延迟、主动坏时钟等反例单独按测试名称识别。不得把这类预期反例中的 CLOCK_UNKNOWN 计作自然故障，也不得把自然故障落入泛化 assertRaises 当作充分通过证据。

PR #3 的历史 CLOCK_UNKNOWN、P2 的历史 CASE_RECEIPT_PENDING，以及本轮修改前 159 项基线中的 PAY/MED 两个 healthy=false 错误，不能全部归因于上述休眠。初次基线运行仅保存了原堆栈，测试清理未保留失败样本/运行账，这是本轮证据缺口；后续诊断已补强，但无法反向恢复已删除的样本。该基线运行时间内没有本轮所捕获的休眠事件。

进一步只读核查系统 timed 服务，发现基线运行期间 12:49:35.272 实际记录了 adjtime 的 adjust=0.045424581、success=1，即约 45.42 ms 的校时处理。该量级超过原 12.5 ms 健康差阈值，与 healthy=false 的症状相容，是另一条具体环境证据；由于缺失失败时原始 C 包，不能把每个基线错误都确定归因于该事件。保留原始校时日志及三行摘录，不关闭 NTP，不更改系统时间，也不通过放宽阈值处理它。

防空闲休眠只处理已证实的休眠路径；它不屏蔽真实校时跳变。宿主时间源偏移超过协议允许范围时，CLOCK_UNKNOWN 是应保留的安全拒绝。部署者应先确认时源已稳定，再按受控恢复步骤重建客户端，依原持久 floor 和授权窗口恢复；不能把一次绿色回归当作时间源永不异常的证明。

因此，本轮能够验证明确运行条件下的统一实现、定位已捕获的休眠故障并保留正确失败关闭/恢复语义；不宣称根治所有历史时钟间歇现象，或保证外部时间源永不失效。最终无休眠联合验收结果与 joint-01 分别保存，不能覆盖或相加。
