## 比赛执行流程复检

实际选定顺序为：受控构造/认证来源与 Basis/Assessment → 必要 V/U 批准 → Permit 与挑战/持有证明 → CommonW.prepare 的非授权凭据 → 当前重验和持久接受 → 原 Core 回执 → 当前领取和唯一 attempt → 一次模拟执行 → 显式 query 原 attempt → 认证终局一次结算。状态读取与审计不推进这些业务步骤。

源码对照覆盖了接受的消费/意图/资源原子保存、回执待签门、领取的依赖与归属重查、EXEC 资格与发送间隙、工具持久效果及认证、可信矛盾、一次结算、当前读取权限。没有把原 Schema 结构合法性作为全部业务检查的替代。

复检中修正的是两处说明/接法：CommonW.prepare 已要求完整批准链，不能按早期草图作为待审批依据生成器；内部状态及单次调用 UNKNOWN 不能直接当原协议终态或覆盖已有终态。这些是当前开发需遵守的集成规则，已经落入[注释页](developer-scope-notes.md)，不归入泛化后置项。

领取后撤销、资格消费与发送间故障的长期未知，以及固定范围/时间/账根迁移则按 N-01～06 明确比赛前提和后续处理。它们是实际行为边界；此次检查不保证未被当前证据覆盖的组合路径不存在其他问题。
