# 比赛范围开发注释

2026-10-12 · 配套 `CORE-SPEC-1.3` [共同安全协议](competition-protocol.md)与[原 R2 对照](r2-application-mapping.md)。下面标明实际行为、比赛暂不扩展的内容和开发时必须保留的前提。后续泛化应按影响重新设计和验证，不能只把固定参数改成可配置。

具体复核用途、业务意图、资源单位和演示结果集中在[比赛开发总交接](scenario-integration-handoff.md)及三个场景交接。共同正文的通用名称不扩大当前固定配置的能力。

## 当前集成应直接遵守的三点

| 位置 | 实际行为与接法 |
|---|---|
| [CommonW.prepare](../../core/common_w.py)与受控场景构造 | prepare 检查已经具备 Basis/Assessment、Review/Authorization、Permit、Challenge 和 CommitProof 的链；缺复核直接拒绝。展示先完成受控依据准备和必要批准，再调用 W.prepare/accept。不要把旧应用草图的“待补批准 Prepare”直接映射到它，也不要为绕过拒绝伪造批准 |
| [CommonW._view / cancel / settle](../../core/common_w.py) | 原字段分别有回执 PENDING、效果 UNKNOWN、取消 CANCELED/NO_EFFECT、结算 SETTLED；这是应用值。展示可说明为“回执待签”“效果未知”“已取消、确认未调用”“已结算”，保留各维度，不能原样塞入 R2 Status 白名单。HALTED 优先停止，即使仍保留先前 SUCCEEDED 观测 |
| [execute_once / query_attempt 返回值](../../core/common_w.py) | 重复 EXEC 返回 EXEC_ALREADY_CONSUMED/UNKNOWN；已知终态从认证 status 读取。工具调用还可能返回 EFFECT_UNKNOWN。新领取时 W.effect_state=UNKNOWN 但 exec_consumed=False，原首次执行仍须过守卫；已消费或消费情况不明不能再次执行。query 后结算是显式受控步骤 |

受控初始化和 complete_receipt 保持受信内部职责；当前没有独立公开调用者认证包装，开发不得把这些方法直接暴露为免认证入口。真实参数与各分支返回见[当前接口](interface-reference.md)：claim 的旧 outbox 状态不是完整终态，工具载荷的成功标签不是验证结论，归属异常也未自动写入 HALTED。

## 比赛暂不扩展的实际边界

**N-01：候选模块与宿主权限。** 当前受控 bootstrap 持有测试角色钥，Windows 同用户的子进程分离不建立文件访问隔离。比赛只让 agent 通过受控候选入口参与，不给它宿主任意命令、账库或密钥访问权。已增加严格 Action 数据入口与签署 caller proof；[能力表](security-boundaries.md)明确角色和密钥边界。这里暂不扩展权限部署；泛化为具有 shell/文件工具的 agent 时，必须建立操作系统权限和服务边界，才能继续声称强制验证独立于 agent。见[初始化](../../profiles/w_seed.py)。

**N-02：领取后的撤销。** W 在新领取事务核当前资格和 DENY；发送阶段及模拟工具检查派发签名、绑定和窗口，没有重新读取全部业务撤销/DENY。因此领取后再撤销，已有派发仍可能生效。比赛把撤销阻断保证限定在新领取前；已领取且 EXEC 未消费仍可能按原守卫首次发送，已消费只可按可用权限查询恢复。这里暂不增加即时撤销设施；泛化须由效果端参与权威排序/栅栏，单独在 W 发送前再检查一次仍留检查至提交的竞争窗口。见[领取/发送](../../core/common_w.py)、[工具执行](../../tools/common_tool.py)。

**N-03：一次执行资格与可恢复活性。** EXEC 标记先持久保存，再发送；两者之间故障可能使效果永远未知、占用长期保留。人工处置权限和禁止重授规则见[处置约定](security-boundaries.md)。当前“查询不到”不会生成有签名的确认无效果终局；模拟工具实际成功分支生成 SUCCEEDED。比赛保留这一保守行为，不实现超时释放、自动重派或自动补偿。泛化若要恢复推进，须增加可靠的“无迟到效果”事实与受控处置协议；把 UNKNOWN 改成失败会改变安全性质。见[发送](../../core/common_w.py)及[工具账](../../tools/common_tool.py)。

**N-04：时间信任与原回执寿命。** 时间认证来自受信本机 OS、固定 epoch 和进程实例；签名包装不提供独立时间来源。原回执 Core 的 kid/iat/exp 固定，过期或原签署资格不可恢复时可能长期待签。比赛暂不实现跨主机/epoch 连续认证或长期换钥观察；开发不能通过更新原 Core 时间或换 kid 补“成功”。泛化需另定时间来源、迁移和历史认证规则。见[事件时钟](../../core/event_clock.py)、[回执签署](../../core/common_receipt.py)。

**N-05：固定范围与状态迁移。** Profile 与完整 scope 一一登记，业务图和否决覆盖来自受控初始化与同 W 发布；worker 证书及工具/容量登记也固定。动态场景行锚定原 C genesis，已有未决操作时直接替换 genesis 可使后续归属检查拒绝并保留占用。比赛暂不提供动态租户/组织、worker 撤换、工具换账及工业复检迁移入口。泛化需有序迁移及未决事实处理；不要通过清库、换 run_id 或改 route/template 释放同一业务意图。见[注册](../../core/common_w.py)、[状态锚定](../../core/w_state.py)。

**N-06：证据独立性与工具真实性。** 工具 hash/checkpoint 核本运行账连续关系，离线核验依赖外部 pin 的受信运行包；一致地回退整盘或替换全部本地根，不由包内签名自行排除。模拟账中的“付款/路由/医嘱”是合成效果。比赛暂不扩展外部防回退锚、现实设备回执或资金/临床设施；泛化须提供相应可信来源和效果认证。见[查询审计口径](query-audit-scope.md)。

**N-07：阻断诊断与持久停止。** 当前可信归属异常拒绝本次领取而保留原 PENDING/占用，没有自动持久 HALTED。比赛先准确展示阶段与首个原因，不把外部诊断表作为永久停止。泛化若需要持久阻断，须经认证和可信复核、成功提交、覆盖全部派发入口，并定义对原查询与占用的处理；同事务先写 HALTED 再抛异常会回滚，坏请求也不能借诊断永久封锁合法操作。当前已实现的工具可信矛盾停止保持原规则。见[接口接线约定](interface-reference.md)。

**N-08：应用结果与理由记录。** 接线分开原观测、本次验证/首个原因和另取的认证视图；视图不可获取不覆盖已有接受/结算。比赛冻结此约定，不引入新签名 Result、自动 H 查询、完整日志或包装服务。应用若保存诊断，先认证并裁剪范围，不能将日志缺失当作未接受证明；广泛接入时另核权限、绑定、时点、并发与存储失败。见[查询口径](query-audit-scope.md)。

三场景的[领取后撤销及重复 EXEC 实测](../../evidence/protocol-review-20261011-boundaries/report.json)确认 N-02 和当前状态接法；其记录展示已有派发继续完成的实际限制，开发不能把这个结果描述为即时撤销成功。

原 R2 的 deps、Review 受众、资格寿命和签名响应差异是具体的消息语义对齐事项，集中见[开发对照](r2-application-mapping.md)。它们不能仅用“以后支持更多场景”解释，也不要求本次为了比赛重新实现全部正式服务；当前比赛通过被签名的 ZJJ-CORE-COMP-1 proto 与原 R2 区分；直接连接原 R2 独立客户端时须明确对应规则并拒绝语义混用。
