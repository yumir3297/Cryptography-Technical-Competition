# 讨论案：面向高后果 Agent 的人类可定义操作约束与密码学可验证动作边界

> 状态：**DISCUSSION / 未采纳、未实施**  
> 记录日期：2026-11-20  
> 所属项目：ZJJ-CORE — 面向高后果智能决策的密码学可验证动作授权与原子接受协议设计与实现  
> 对照对象：仓库 `main`（记录时观察到提交 `2d5370fd6aff69762b162908dcfe136e99ae99d4`）及其协议、安全边界、Agent 接口和执行核心。  
> 用途：保存研究讨论、定义待验证问题、指导后续设计评审；**不是协议规范、正式威胁模型、实现任务单或已通过验证的创新声明**。不修改既有 wire 标识、Schema、密钥、执行代码及已有实验结论。

## 1. 背景与研究对象

研究对象暂定为“高后果执行型 LLM Agent”：模型参与形成具体动作，通过工具、API、服务或设备控制接口可能改变资金、生产设备或其他高后果业务状态。这里的“高后果”指错误动作具有较大损失或难以恢复的风险；LLM Agent 不是唯一能够自主执行现实动作的系统，传统自动化同样存在错误、级联故障和检查/使用之间的竞态。

本轮讨论的核心观察：

- **沙箱隔离与外部动作授权是两类互补机制。** Agent 可以在沙箱中推理，但其合法业务能力最终要跨越边界调用外部工具；只保证运行环境隔离，不能自动保证现实动作经过有效授权。
- **模型推理结果不是授权事实。** Agent 可利用不可信网页/工具返回内容形成动作；真实权限应由独立受信机制和已认证的人类/组织规则决定。
- **签名正确不代表业务正确。** 签名只能证明相应主体对特定消息作出认证声明；不能自行证明传感器真实、用户语义意图正确或物理效果符合预期。
- **Agent 的动态规划会放大组合风险。** 多步工具调用、重试、重规划、短期状态变化、跨动作预算与依赖关系可能使每个局部合法的操作合起来违背原任务约束。
- **执行安全不止于批准。** 必须明确“提出—授权—接受—领取—执行—效果确认—结算/审计”的不同事实和失败恢复语义。

## 2. 本轮达成的设计方向（仅作为提案）

### 2.1 三段责任与强制边界

初步逻辑链：

**Agent 提案端 → 独立受信的动作寄存/控制中间层 → 受控工具执行端 → 可验证回执与状态反馈**

| 位置 | 应承担的职责 | 不应承担或不应信任的部分 |
|---|---|---|
| Agent | 理解目标、规划、提出结构化候选动作、读取必要的脱敏状态 | 不自授高后果权限；不持有批准/执行私钥；模型输出的风险结论不构成可信判定 |
| 人类/组织授权者（控制面） | 预先定义允许的操作类型、任务范围、限额、前置条件、审批条件、失效规则；必要时单笔复核 | 不等同于每次都手动签字；网页点“同意”本身不等于可核验的自然人密码学签名 |
| 受信中间层（数据面） | 解析和寄存请求、读取受信规则与状态、独立核验、持久处理去重/占用/接受、形成可验证派发及证据 | 不是普通代理转发器，也不以第二个 LLM 的自我审查取代确定性门控 |
| 工具执行端 | 独立验证派发凭据、冻结动作及目标工具绑定；控制真实操作、生成可关联的可信反馈 | 不应只依据 `approved=true`、请求来源 IP 或 Agent 自报角色执行 |
| 审计/独立验证方 | 离线核对签名、对象引用、状态转换、回执与版本连续性 | 不应把“日志存在”直接解释为现实动作无误 |

**非绕过要求：** 若 Agent 仍可直接用另一个高权限 API 密钥调用生产工具，中间层就不是强制安全边界。真正的执行端必须只接受其授权契约要求的请求；实际生产隔离和凭据保管仍是额外信任前提。

### 2.2 人类应先定义“操作秩序”，而不只是逐笔审批

用户提出的新重点是：**人可以通过中间寄存端介入，对整体各类操作进行定义**。建议未来区分：

1. **策略定义（Policy authoring）**：哪些任务/Agent 可使用哪些工具、动作参数范围、累计预算、审批升级条件、依赖顺序、状态前提、有效期与撤销语义。
2. **可信发布（Policy publication）**：由具备权限的控制主体认证发布、版本化并留下可验证引用；发布者的身份、授权来源与规则版本需要独立核验。
3. **自动执行门控（Deterministic enforcement）**：中间层逐项检查 Agent 提案是否满足当前有效规则。
4. **例外人工复核（Escalation / review）**：超过阈值或不可确定的场景需要指定主体复核；不得用人工批准覆盖不可绕过的物理安全联锁。
5. **执行与审计（Execution / evidence）**：形成与策略和动作关联的唯一接受事实及工具效果证据。

举例：管理者预先允许 Agent 在某产线将速度调整到 50–85 的范围、同一任务最多调整三次、设备温度超限则不得执行；Agent 可以自主决定是否调整，但不能只因“模型认为合理”突破授权边界。这里的数字只是解释性例子，不是现有 IND 实现参数。

### 2.3 “全局相关量”要组织为可验证关系，而非把所有原始信息塞入一个签名

用户提出的第二个重点是：**将影响一次动作是否可以接受的全局相关量，在中转层与两端的通信中组织起来，形成密码学可追溯性与匹配性。**

候选关系对象（尚未确定 wire 字段）：

| 关系 | 候选承诺/核验内容 | 权威来源 |
|---|---|---|
| 人类/组织规则 ↔ 任务 | Policy ID、修订号、授权主体、TaskRef、范围、有效期 | 认证的控制面和策略发布者 |
| 任务 ↔ Agent 提案 | 任务身份、Agent 身份、操作目的、候选动作及原始上下文引用 | 可信任务登记＋不可信提案输入 |
| 提案 ↔ 冻结动作 | ActionHash、参数、工具、版本、目的地、操作唯一 ID | 受信解析/构造器与签名认证 |
| 动作 ↔ 受信依据 | PolicyRef、BasisRef、EvidenceRefs、RequiredDeps、状态/版本承诺 | 可信来源及独立验证器 |
| 已批准动作 ↔ 实际派发 | COMMIT/Acceptance 引用、派发签名、唯一 attempt、消费记录 | W / 受控执行入口 |
| 派发 ↔ 执行反馈 | 原 attempt、工具账身份、效果摘要、终局事实及状态引用 | 独立验证的工具效果端 |

**设计约束：** 对静态、可认证且有安全意义的关系使用规范化字段与签名/哈希引用；对动态状态采用受信状态读取、版本检查和原子更新。签名不会自动保证被引用事实真实或实时，也不会自动解决网络与数据库事务一致性。避免签名覆盖无关大量数据带来的隐私、频繁重签和状态陈旧问题。

### 2.4 主要威胁与安全边界

讨论关注：不可信网页/工具结果引导的目标偏移、恶意/故障 Agent 提案、动作参数替换、跨任务权限扩大、授权失效后使用、重复提交、重规划引入新依赖、局部合法但累计越权、执行超时导致效果未知，以及工具回执不匹配。

参考的两组安全思想：

- **Lethal Trifecta**：同一 Agent 同时具备私有数据访问、不可信内容读取、任意对外通信能力时，会形成危险的数据外传链；在架构上应避免高风险能力组合，配合独立工具授权。
- **推理、授权、执行、验收分离**：不能由模型自行审查并证明自己的动作安全；权限边界应尽可能采用确定性、不可由 Agent 篡改的执行机制和审计依据。

暂不宣称能够覆盖：宿主 OS 或根密钥被完全攻破、生产设备物理故障、传感器故意伪造的现实状态、多机恶意回滚、任意跨系统的物理 exactly-once、所有提示注入、用户自然语言意图的完备形式证明。这些需要单独威胁假设和互补机制。

## 3. 与现有 ZJJ-CORE 主线实现的比较

静态检查依据为文档和源码；此处的“已有”表示在当前可见代码或声明中存在对应路径，**不等于本次新做了端到端复测**。

| 维度 | 现有可见实现 | 新提案的增量或待验证问题 |
|---|---|---|
| Agent 边界 | `competition/agent/mcp_server.py` 仅提供 `zjj_propose` 与 `zjj_status`，不暴露批准、执行、结算能力 | 面向更多种类的工具动作，维持强制非绕过 |
| 受信字段构造 | `application/trusted_action_resolver.py` 基于认证 Task/Policy/角色等补全工业 Action | 明确支持人类定义的新操作类型与条件，不能任意让 Agent 自带权威字段 |
| 控制面发布 | `core/trusted_state.py` 已可根签发布 POLICY/TASK/KEY/ROLE 等，含版本检查 | 人类可操作的通用策略定义、权限委托与变更审计；不应混同现有单笔批准 UI |
| 人工审批 | `client/approval.py` 的可选等待室和 `console` 控制台可逐次放行 G/U/V/X；默认自动路径属于模拟角色 | 建立策略级人类授权、按风险触发复核及可证明的真实管理者身份 |
| 密码学关系 | `support/wire.py`、`core/authorization.py` 已有 ActionHash、Ctx、PolicyRef、BasisRef、Refs/Deps、认证签名 | 研究跨动作任务目标、累计约束和动态状态承诺，避免重复发明已有字段 |
| 接受与恢复 | `core/common_w.py` 已有单机原子接受、意图墓碑、执行资格消费、唯一 attempt 与未知效果处理 | 扩展并验证策略变更与重规划交错时的状态语义，不能把 W 原子性误说成物理原子性 |
| 工具端验证 | `tools/common_tool.py` 验证签名派发、动作绑定、工具账及效果记录 | 建立真实 API/设备适配的强制门控与可信反馈，但真实设备尚未验收 |
| 场景覆盖 | 工业单机全流程主演示，PAY/MED 主要为本地模拟补充；共同核心复用 | 先选一类高后果操作作为研究样本，再判断通用化边界，勿声称三场景生产支持 |

现有协议已经是“多对象认证引用链＋有状态接受”，并非只是多位参与者分别签名。新方向更多在于**由人定义全局操作规则**以及**跨动作、跨状态的持续匹配**。

## 4. 可研究的核心问题（目前均为假设，不是创新结论）

**RQ1 — 可验证的人类定义操作规则**：在一组清楚定义的 Agent 动作类型下，能否使人类/组织发布的任务级策略被中间层和执行端独立核对，且 Agent 无法自行扩大权限？

**RQ2 — 全局匹配与状态有效性**：能否明确哪些全局量必须进入密码学承诺，哪些必须在接受/领取/最终执行时重新读取，并证明在既定并发和撤销假设下不会接受已经不匹配的动作？

**RQ3 — 多动作约束**：Agent 动态重规划后，如何核验单笔授权与整体任务级顺序、累计预算、资源占用和必要依赖的一致性？

**RQ4 — 有故障的动作接受与证据**：在网络中断、重复提交、状态更新交错、响应丢失时，能否使授权消费、接受事实和执行证据保持可审计的一致关系？对物理效果未知应保留 UNKNOWN，不臆断失败后重新执行。

**新颖性审查要求**：上述方向与 NIST Zero Trust PDP/PEP、能力安全、MCP 工具授权、交易绑定（如 AP2）、工作流证明（如 in-toto）、事务和幂等处理均存在明显交叉。未来必须逐项与现有方案和已有学术论文对照，不能因为使用 Agent 或加了一层中间件就认定创新。

## 5. 后续研究与实验建议（尚未立项）

建议先围绕一个可控场景、一个明确安全性质构建差异化测试，不急于修改共同协议：

| 实验情形 | 期望被核验的性质 |
|---|---|
| 不可信网页/工具反馈诱导 Agent 改收款人或工业操作目标 | 只有满足独立人类授权范围的具体动作能被执行 |
| 已签授权后修改参数、工具或目标设备 | 冻结动作与派发不匹配时拒绝 |
| 执行前状态版本变化、撤销、资格过期 | 按定义的检查点阻断或重新获取有效依据 |
| 合法单笔动作累计突破全任务预算/次数 | 跨动作累计规则不能被拆单绕过 |
| 重规划增加新依赖或换任务分支 | 必须重新核验受信依赖与原任务授权 |
| 网络断连、重复提交、未知工具效果 | 不能仅因超时重复实际执行，证据指向原 operation/attempt |
| Agent 绕过中转直接请求真实工具 | 生产执行端在配置正确、私钥未泄漏的前提下强制拒绝 |

评价时同时记录：未授权动作接受率、合法动作误拒率、检查延迟/吞吐、策略规模增长成本、恢复正确性、审计核验可重现性。比较基线至少区分：仅工具权限、普通 API 代理/策略网关、当前 ZJJ-CORE 机制、拟议增强。测试通过也只能声称覆盖所定义威胁与场景。

## 6. 暂不决定的事项

- 人类规则适用的操作语言/DSL、签发角色、有效期与撤销权限模型。
- 全局上下文究竟需要哪些签名对象、哈希承诺和不可变状态引用；是否引入任务级依赖图。
- 中间层与现有 C/Resolver/W 的职责对应，是否只是现有组件的控制面增强，避免叠加第二套状态账或平行授权核心。
- 策略升级与在途操作的精确定义，尤其“领取后撤销”能否阻止效果端执行。
- 选用真实设备、资金模拟账户或其他场景进行下一阶段研究，及必要的物理安全联锁。
- 成立的可证明安全性质、受信假设、形式化模型、对照基线和论文新颖性结论。
