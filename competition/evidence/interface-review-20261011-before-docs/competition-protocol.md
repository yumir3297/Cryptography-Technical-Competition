# ZJJ-CORE 比赛版安全协议

版本 `COMP-PROTOCOL-FINAL-1.0`，2026-10-11。适用源码与证据见[交付入口](../../FINAL_PROTOCOL_HANDOFF.md)。原消息线版本保持 `ZJJ-AAP / 2.6`；本文是比赛说明及应用规则对应说明，结构字段和编码引用既有 R2 合同和 Schema，比赛应用约定另列对照。

## 1. 设计目标与适用范围

在 agent 参与的高风险、高后果流程中，动作建议与执行权限分离。在受信执行边界内，agent 可提出候选动作；受信核心独立验证身份、来源、批准、安全条件和执行约束，满足条件后才允许模拟工具产生效果。机制用于阻止未经授权、条件不满足、动作替换和重复执行，降低失控自动化造成的人员负担与后果风险。人的必要批准绑定具体动作；协议不以签名代替业务判断，也不作 agent 永不出错或免除人的责任的承诺。

比赛采用受信单机、固定登记范围和三个签名模拟工具：工业分拣、合成付款、合成医嘱登记。固定范围使来源、资格、适用否决和资源可以由同一权威序列完整检查；模拟工具提供可读取的独立持久效果账与签名终局，便于验证故障恢复。模拟结果分别表示路由登记、模拟付款记录和合成医嘱登记。

信任前提是控制者 C 的登记与发布、来源 E 的认证、W 验证及持久账、受控签名者和工具账可信；单机操作系统、时钟及初始化管理受信。agent 和提交者自报的公钥、角色、风险结论、依赖列表、成功标志均不能直接授予权限。验证依赖密码算法与公钥登记；签名证明认证者对所绑定内容的认证，不独立证明来源所述现实事实。

## 2. 参与角色与动作绑定

| 角色 | 职责与权限依据 |
|---|---|
| agent / 候选模块 | 提出动作；不直接访问执行出口或授权私钥 |
| C | 登记密钥、主体、角色、用途、范围、策略、当前版本和资源 |
| E | 认证场景来源；其来源资格和业务范围另行检查 |
| H | 以当前登记身份提交请求、持有证明及读取请求 |
| G | 依据验证链签发 Permit |
| U | 对同一动作给出必要 EXECUTE 批准 |
| V | 对独立推导的用途复核；工业 QUALITY_REVIEW、付款风险复核、医疗 CLINICAL_REVIEW |
| X | 认证挑战和冻结 Acceptance；资格不因持有私钥而自动成立 |
| W / 受控 worker | W 独立检查并记录接受、领取及结算；worker 凭当前认证职责触发相应步骤 |
| 模拟工具 | 验 W 签名派发，固定原 attempt 的效果事实并认证查询结果 |

完整 Action 绑定 scope、operation_id、业务主体、H 身份和 kid、X、tool/version/destination 及场景 payload。ActionHash 按原独立域承诺完整动作；Basis、Assessment、批准、Permit、Challenge、CommitProof、COMMIT、Acceptance 和工具请求通过原 Ctx、Refs 与 AH 指向同一动作。任何字段改变须重新建立依据并签署，派发使用冻结 Action。

密钥必须来自 C 登记并通过用途、角色、范围、版本及当前资格检查。主体分离按登记 subject 判断：U 与 G/X 分离，必要 V 与 U/G/X 分离；H 与 U 可为同主体。每份签名均核验，Ref 相同不代替验签。

## 3. 授权条件及机制目的

| 机制 | 条件与设计作用 |
|---|---|
| 认证来源与独立重算 | W 从当前 C/E 对象重建 Basis、Assessment、required_reviews 与 RequiredDeps；不能通过删依赖或自报安全结论绕过条件 |
| 必要批准与否决 | 每个必需用途须有精确绑定的 APPROVE，另须 U 的 EXECUTE；查注册范围完整否决历史，后续批准不擦除既有适用 DENY |
| 读取与业务权限 | 先核读取资格再读敏感输入/调用候选；签名用途、scope 和工件/账户/患者等业务范围共同约束操作 |
| 当前性与时间 | 接受、回执发布、领取及终局认证分别检查当前条件，准备时的成功不缓存成后续执行权 |
| 稳定意图、资源与在途 | 业务意图永久去重；同一接受序中检查容量、累计次数和任务在途，防止换操作号、route/template 或重复请求增加权限 |
| 冻结回执与唯一 attempt | 接受事实和派发内容固定；认证恢复不能改动作，执行恢复不能生成第二次执行资格 |
| 未知与可信矛盾处理 | 状态未知留占用、只查询；经认证且绑定正确的不可变事实矛盾停止，避免将不明结果当作可重做 |

判定为三值：有明确不满足条件 F 则拒绝；无 F 而有未知 U 则暂缓；全部 T 才推进。原 R2 时间规则为 `iat ≤ lo` 且 `hi < exp`；明确到期为 F，区间跨界或时钟/来源无法确认时保守为 U。当前性按 W 接受的认证发布顺序与逻辑时间判断。

比赛依赖集合采用从可信有限对象图重建后的精确比较；IND/MED 中不属 wire Dep namespace 的来源/身份/包对象通过认证原文与传递引用检查。完整否决覆盖来自 C 认证初始登记和 W 唯一发布序列，适用键绑定 Profile、完整 scope、operation、Basis 和必要用途。在完整初始化和唯一发布入口的前提下，W 检查该范围内全部已登记的适用否决。

## 4. 接受、回执与状态转换

1. 受控准备流程认证来源、动作与身份并建立 Basis/Assessment，再收齐必要批准、Permit、挑战和持有证明。W 对已构成的链作接受前检查，返回短时准备凭据；当前实现称 ticket，它不授予接受、资源占用或执行权限。
2. W 在接受序列点独立重验全链、当前性、批准/否决、唯一性和资源。全 T 才原子持久保存消费、意图墓碑、预占、在途、COMMIT、冻结 Acceptance Core 及派发意图；接受前失败不新增这些业务事实。
3. 先固定 COMMIT，再求其 RecordRef，继而固定 Acceptance Core 和 Ref，避免摘要循环。`accepted_at` 是最终受信逻辑守卫的 lo，持久提交形成唯一接受事实；不把 lo 宣称为物理落盘瞬间。
4. 接受提交后 X 读取原 Core，在当前签署资格及原窗口内签署；保存回执前再核原字节、签名、资格与窗口。签署失败或资格失效保留已接受事实与占用，显示回执待签；合法回执保存后才允许领取。
5. 恢复原 Core 不换 kid、iat、exp 或 Ref；已保存回执返回原字节。提交应答丢失先认证查询原事实，通信超时不证明回滚，不授权重新接受。

| 事实维度 | 合法变化 |
|---|---|
| 接受 | 未接受 → 已持久接受；终态仍保留原接受和意图墓碑 |
| 回执 | 已接受待签 → 原 Core 已合法签名；到期/不可补签仍保留原接受 |
| 派发 | pending → started，唯一 attempt；确定失效且证实未领取的 pending 可取消；started 永不回 pending |
| 效果 | started 无可信终局为 EFFECT_UNKNOWN；可信成功为 SUCCEEDED，权威确认无效果且不会迟到生效为 FAILED_CONFIRMED；可信矛盾为 HALTED |
| 结算 | 原 FinalFactID 至多一次结算；相同事实的新认证只增加证明，不重复业务记账 |

“已接受”“已签回执”“已领取”“模拟效果已确认”“已结算”是不同事实。应用内部 pending 派发不等于原 R2 Result 的 PENDING（已登记未接受）。应用待签状态不输出为缺少可验 Acceptance 的正式 ACCEPTED。

## 5. 派发、恢复与结算

领取须重新核 dispatch_before、当前来源/资格/批准/否决、工具映射、非自身变化的依赖和本操作占用。接受必然改变的 Behavior、Flight 和场景行按冻结后见证及归属检查；来源、任务、外部控制变化不获豁免。全 T 才原子领取并生成唯一 attempt，冻结原工具/ledger 和签名派发。

在唯一受信执行入口和持久账前提下，EXEC-0 限制每操作应用层执行调用至多一次。一次资格先持久消费，再调用模拟工具。消费与实际发送之间可能故障，恢复仍只查询原 attempt；协议选择保持未知并保留占用。实际发送、执行资格和已确认效果分别计数。

工具验证完整冻结动作、AH、operation、attempt、COMMIT/Acceptance、工具信任与原账绑定；效果、去重和不可变终局一起持久保存。查询只读取和重新认证同一事实，不执行。查询不到不构成 FAILED_CONFIRMED。

W 首次结算须核工具当前认证、窗口、原派发及账连续性；按原 FinalFactID 更新资源与在途一次。认证时间、签名或 RecordRef 变化不改变事实身份。坏签名/错绑定输入拒绝；通过认证和绑定后的不可变事实矛盾使 HALTED，保留账与调查证据，不自动重派、释放未决占用或补偿。确定未领取的取消属于 W 确认的无效果终态，不能伪造为工具 TOOL_FINAL。

领取守卫保证该序列点的当前性。比赛模拟工具还核签名与执行窗口；领取后新的外部撤销、真实机械期限及现实效果真实性需各自工具环境提供相应保证。

## 7. 演示结果

已有共同 W 运行包包含 22 个具名场景：三 Profile 的正常、工具提交后丢应答、未知查询、并发领取/结算、可信矛盾和 W 提交后退出，以及工业的四个竞争场景。另有跨 Profile 同 operation_id 的三个子例。正常路径均为 1 接受、1 attempt、1 观察发送、1 模拟效果、1 结算；恢复不新增执行。所选缺复核及读取拒绝展示另见本轮六例验证。

证据等级分别记录规则已定义、组件已验证、端到端已运行；工业二阶段复检和长期工具换钥属于已定义规则，不由本次 INITIAL 单阶段或同钥再认证演示代替。正式 39 项、原 21 组总目标和历史研究记录保持各自身份；本次比赛协议材料不以全量科研验证或软件产品化作为完成门槛。
