# 协议时间补全：二轮合同审查

日期：2026-10-10。角色：独立合同审查。审查对象：`01_core_contract.md`、`04_tool_final_recovery.md`、`05_time_acceptance_recovery_PROPOSED.md` 以及三 Profile 的现有结构 Schema。本文提出候选精化要求，不修改 R2，也不声称已经实现新合同。

## 1. 审查结论

推荐“接受事实永久冻结，当前认证仅增加观察证据”的方向成立于明确的可信 W/C/X 前提。要从语义草案进入可复现机器合同，必须同时固定：独立对象类型与签名域、原 Core 的无签名类型、当前请求绑定、当前认证资格、权威历史来源、状态快照与历史事实的分离、三值失败及无副作用规则。

最大的证据边界是：R2 COMMIT、凭据见证和原未签 Core 不是独立于 W 的历史证明。它们能被重新计算和交叉核对，但历史全 T 检查、真实持久接受、没有账回退/分叉，仍来自正确 W 的归档与 C 批准的连续历史入口。研究验证器必须把这些事实标成显式 oracle 前提，不能用一个自建字典中的 `true` 冒充独立证据。

## 2. 原 R2 已固定的承重结构

- `AcceptanceCore = {protected,body}`；它不含 `sig`。`Ref` 以 protected/body 为输入，所以原 sig 从未生成时仍有原 Ref。Core 与完整 Acceptance 必须作为不同类型解析。
- 原 Core.payload 只带 ctx 与各承重引用；完整 Action 来自 COMMIT/BASIS。校验须核 `AH(profile,COMMIT.value.action)`、ctx 全字段、COMMIT.action 与 frozen_tool_request 相等，不能以客户端 Action 代替。
- COMMIT 是来源经认证的 Record，没有 Envelope 的 sig 字段。`RecordRef` 仅承诺内容，不认证发布者、持久提交或内容真实性。
- `credential_witnesses` 保存当时资格/公钥和 W 检查序号；它没有把资格 Grant 自动变成可离线验真的 C 签名证书。KEY/ROLE Grant 在原合同中通过 C 受控发布，不能虚构不存在的 C Envelope。
- 原 R2 Bundle 只允许完整 Envelope 或 Record。缺 sig 的原 Core 不能作为一个假的 Envelope 附件；新对象不能伪装为原 Acceptance。
- 原 KEY_GRANT.purposes、Role、ResultCode、Bundle 对象分支和引用类型都是固定枚举。因此观察用途/对象/响应的新增必须显式隔离，不能声称原 R2 解析器自然兼容。

## 3. 推荐的机器合同结构

以下名称供精化选择，不是正式 R3 标识；最终候选须选择一套唯一的名字和精确字段，不保留别名或隐含默认。

### 3.1 独立外壳与域分离

顶层对象应有固定 `contract`，例如 `TIME-CLOSURE-PROPOSED-0.2`；原 R2 `version="2.6"` 只描述嵌入原对象，不表示整包是原 R2 Envelope。新认证必须具有明确 `kind="ACCEPTANCE_OBSERVATION"` 和 `purpose="HISTORICAL_ACCEPTANCE"`，且用新的显式签名域，例如：

```text
ObservationToSign = Enc(["ZJJ-TIME-OBSERVATION-PROPOSED-v1", contract, protected, body])
ObservationRef    = SHA256(Enc(["ZJJ-TIME-OBSERVATION-OBJ-PROPOSED-v1", contract, protected, body]))
OriginalCoreDigest = SHA256(Enc(["ZJJ-TIME-ORIGINAL-CORE-PROPOSED-v1", contract, original_core]))
```

签名只采用原严格 Ed25519 验收规则；签名域把新认证与原 `ZJJ-SIG-v1` 分开。事实 ID、档案摘要及当前状态快照也各有独立域，不能在不同类型库中尝试解释一个摘要。`original_acceptance_ref` 继续按原 R2 Ref 算法，不把新观察 Ref 写进去。

所有字段必需且 `additionalProperties=false`。N/Time、Base64url、精确 Scope/Profile、受限 JCS、重复键拒绝、大小/图深限制沿用原定义；JSON Schema 结构通过不能代替语义检查或原始字节检查。

### 3.2 不可变事实与附件

事实最少绑定 `profile,scope,operation_id,action_hash,ledger_origin,accept_seq,accepted_at,commit_record_ref,original_acceptance_ref,original_core_digest`。其中 ledger_origin 是历史权威命名，不因换钥而变化，但字符串相等没有连续性证明效果。

原 Core 附件精确为 `{protected,body}`，protected.type 必须 Acceptance，其内部 proto/version/profile/alg 必须是原 R2 常量。不得设置 `sig=""` 或 `sig=null`。如果另附原完整 Acceptance，必须核它的 Core 逐字等于原 Core，并用原归档公钥严格验签；其存在与否不得改变事实 ID。

COMMIT 按原 Profile 精确 Schema 验收并核 RecordRef；Core 所有重复 ctx/permit/proof/authorization/review/seq/time/COMMIT/dispatch 字段必须与 COMMIT 逐项相等。接受时间必须为 trusted_time.lo，区间宽度不超原上限。原 COMMIT 不加新 acceptance_ref 或签名字段，避免回引与改写。

不能仅检查某次接受的最终 CORE/COMMIT 摘要就宣称原授权历史全 T。完整历史验证必须解析原承重图与当时状态/撤销/覆盖集合/事务见证，或明确调用经认证 W 的历史审计 oracle；缺少这一步应为 U，不能默认为 T。

### 3.3 当前查询与作用域绑定

新观察必须绑定一份具体的新鲜请求：`request_ref,operation_id,attempt_id,challenge_ref,session_id,nonce,requester,requester_kid`；scope/Profile 必须与原操作相等，aud 精确为该已认证 requester。Challenge 必须绑定当前 H/Task 委托与 op，且 QUERY/OBSERVE 用途不得被解释为 COMMIT 用途。

如果复用原 StatusQuery，服务端与客户端必须预先固定新观察运输合同，并核原 Request/Challenge 完整签名和当前资格。若需要通过网络选择响应合同，则合同选择必须在新请求签名内，不能靠未签 HTTP 参数协商或默认回退。原过期 StatusQuery 不得仅靠重新签署观察变成当前请求。

目前草案把“已认证 EXISTING 观察请求”列为可选，但尚未定义其字段和副作用。初次精化建议仅提供新 STATUS 查询观察路径；EXISTING 路径须另给当前查询鉴权与请求绑定定义后再纳入，避免扩大本轮模型。

### 3.4 当前资格与可信映射

观察者应由独立 C 受控登记授予新目的，例如固定 `ObservationTrust` 记录：contract/profile/scope/observer_subject/observer_kid/public_key/purpose/ledger_origin/epoch/iat/exp/root_generation。还须固定到当前 POLICY 的 executor subject、用途与 Profile 工具/目的/业务范围；不是“同 subject 的任意有效钥”。

新目的不能从旧 Grant 中自行推导。选择新增 KEY_GRANT.purpose 或独立 ObservationTrust 都需要新合同；若用独立记录，须说明它经 C 认证发布，不声称其裸 JSON 自带 C 签名。

生成新认证时，查询者 KEY/ROLE/Task 委托、观察者当前 KEY/ROLE/新目的、当前映射和同账授权均为 T；在 W 同一事务序或受保护控制快照中重验。签署预计算不能把旧允许决定直接带过撤销。接收端当前检查也必须明确其观察时点：生成后发生撤销时，接收检查 F/U 应拒绝或暂缓该新认证；不宣称签名之后永久有效。

### 3.5 档案与连续历史

档案接口至少返回原操作真实 durable commit 决定、原 Core/COMMIT/承重图、原当时资格与状态见证、账身份及经 C 认证的连续历史入口。跨根代移交/备份恢复必须明确原账高水位、墓碑与没有分叉/回退；仅匹配 ledger_origin/root_generation/revision 数值不证明它们真实。

研究程序可以接受 `historical_authorization`, `durable_accept`, `ledger_continuity`, `archive_integrity` 等显式 oracle 三值输入，但测试结果只能证明“前提 T 时的合同转换行为”。如果希望声明实际历史完整性，就需要独立审计实现或更强的外部透明日志/签名账证明，本轮不能由哈希定义自行得到。

连续性未知或档案暂不可取为 U；已知不匹配/损坏为 F。已知接受存在但无法得到可信认证时仍为通信未知/待恢复，不能返回表示从未接受的 REJECT 或 status=NONE。

### 3.6 当前状态与历史接受分离

历史事实只能说明过去那笔接受成立；不能把 observation 的事实内容当成当前 status。新的签名响应需要额外绑定 `{request_ref,operation_id,status,status_seq,snapshot_seq}` 以及 snapshot 可信读取时点和当前 ledger 身份；status 来自同一次当前 W 快照。

观察签名与状态快照若分成两个对象，应互相通过显式 snapshot_ref/fact_id 绑定并使用同一查询身份。若签在同一包中，语义仍需分清 immutable_fact 与 current_snapshot。当前状态可能是 ACCEPTED、EFFECT_UNKNOWN、SUCCEEDED、FAILED_CONFIRMED 或 HALTED，过去接受的 accept_seq 不能代替当前 status_seq。

## 4. 必须固定的失败与副作用规则

认证原事实成功的增量严格为：accept_count=0、permit/nonce 执行权消费=0、resource_reservation=0、dispatch_attempt=0、tool_call=0、settlement=0。查询 nonce 消费与查询响应审计按新查询合同允许，不能泛称“所有 nonce 均不消费”。

完全相同旧请求重传只返回已经保存的旧完整响应；原响应不存在时仍待恢复。新查询才允许当前新签名和新状态。旧恢复包重放到另一次查询因 request_ref/nonce/attempt 不同应失败。

不同 Ref 不意味着相反事实；同事实多次当前认证可有不同签名时间/kid。只有通过当前认证且同作用域/原操作/账/序号绑定的不同事实，才构成可信完整性冲突。垃圾签名、错 scope/op/ledger 的包先拒绝，不能触发 HALTED。

新的认证无权改原 Core/Ref/接受时刻/许可消费/稳定意图墓碑；也无权延长 dispatch_before。已经 started 的操作只能走原 attempt 的 TOOL_FINAL 再认证与一次结算。

## 5. 验证优先级与可宣布结论

最少独立向量应覆盖：原 sig 从未存在、旧钥撤销与新目的合法注册、原 Core 各字段替换、COMMIT/Action/AH 不一致、错 op/scope/profile/ledger、请求重放/替换、陈旧状态快照、当前目的或映射撤销、可信时间跨界、连续性未知/回退、完全相同事实的新认证、经认证相反事实与垃圾包区分、晚于派发截止的成功观察且零执行。

应分别报告结构通过、真实 Ed25519/Ref 正反向量、合同验证器对 oracle 前提的行为、状态模型安全性质及产品未验证项。只检查自己构造的一份正常包不足以证明历史安全；单实现通过也不能声称完整互操作或完整形式化证明。

在精化产物完成后可以确认“在可信 W/C/X、连续历史、真实当前资格和有界成功通信机会下，原回执不可补签不再阻止客户端认证既有接受事实，且认证不新增执行权”。无界延迟、永久账丢失、恶意 W 或设备端物理执行期限仍不是无条件可解决的目标；必须在最终结论中保留这些前提。

## 6. 后续精化稿复核

已只读复核 `06_time_observation_candidate_contract.md` 首稿。相对 0.1，该稿已经明确独立 proto/version/Query、无 sig 的原 Core、完整规范 Package 的可信发布、独立恢复高水位、逻辑发布资格时点和当前查询身份。它也明确历史快照不承诺接收时全局最新，避免把过去接受等同当前执行授权。

### 6.1 首稿须修订项

**Major M1：发布必须核对受信冻结读取见证。** 首稿 §5 步骤3重查历史/当前资格，但未逐字段规定候选 `Archive/Fact/Snapshot` 与步骤1同一受信读取记录相等。反例是密码正确的候选带真实 Fact，却改报 status 或 status_seq；只验签、验原档案、验当前资格仍不足以判断它是不是实际 W 状态快照。应持久或受保护保存 `FrozenReadWitness`：QueryRef、完整原档案摘要、FactID、status/status_seq/observed_time、控制revision、账epoch与锚，并在发布时精确比较；这一见证来自 W，不是客户端附件。

**Major M2：当前授权元组必须是全部资格的交集且覆盖变化。** 首稿可信当前元组只有一组 iat/exp/active，KEY、ROLE、新目的、操作访问权和当前观察映射可能独立到期或撤销。应分别核验，或明确 `iat=max(全部起点), exp=min(全部终点), active=全部当前有效`；任何未知产生 U、任何明确失效产生 F。控制revision必须因每项撤销、授予、映射和Task委托改变而严格推进，不能只覆盖一种角色变化。

**精确化建议 C1：观察者映射选择。** 新 HISTORY_OBSERVER 可以独立于原 EXECUTOR；无需强迫它等于旧业务 POLICY.executor。但须由 C 明确固定本服务当前 subject/kid 的 scope/ledger 权限，或明确批准集合并由 Query.aud 选定一项。不能把同subject任意有效钥当成当前业务映射。

**精确化建议 C2：挑战窗口不可续命。** 可信挑战记录须明确 session/nonce/subject/kid/op/aud/attempt 和产生/过期时刻；Query 必须在该记录窗口内，exp不晚于挑战exp，不能拿旧nonce重新签一份未来Query来恢复资格。记录的权威性来自受控 W，不是客户端自报“存在”。

以上为精确合同完整性问题，尚未判为已实现漏洞。须待修订合同和机器检查器一起复核。A1–A6仍是明确前提，研究检查器不能由这些输入证明真实基础设施满足前提。

### 6.2 精化合同与机器检查器最终复核

已只读检查更新的06合同以及 `verification/protocol_time_closure_v2/codec.py`、`observation.py`、`fixtures.py`、`schema.json`、`test_codec.py`、`test_observation.py` 的承重路径。M1已通过明确 FrozenReadWitness 和候选包逐字段比对修复；M2已通过完整授权交集及全部变化推进控制revision修复。C1固定受信观察者映射、C2挑战身份/窗口绑定也已明确。

独立审查发现并复现一项额外时间实现问题：Publish 使用区间上界 hi 保存“持久下界”，会将未来可能时刻当成已知下界。例如合法发布区间 `[1102,1104]` 后，合法接收区间 `[1103,1103]` 被错误判 `U/CLOCK_UNKNOWN`。父任务已改为 `max(旧下界,发布lo)`，接收的序约束也只使用发布lo。独立再次执行该轨迹得到 floor=1102、接收 T；该反例已关闭。此修复避免误拒绝，不增加执行权。

承重审查结论如下：

- 客户端输入只提供规范 Query/Package 字节；当前公钥/用途/角色/范围、可信挑战、历史完整性/连续锚、FrozenReadWitness、已提交Publication来自受信适配器输入，不从客户端包自授。
- 验证器严格验双签名、当前授权交集、请求/nonce/受众/作用域绑定、三Profile原Core/COMMIT结构、原AH/Ref/RecordRef和FactID；Archive明确无原sig，恢复不承诺原sig曾存在。
- Snapshot与受信FrozenRead精确相等；之后 W 状态已变化时仍可返回明确带观察时刻/序号的旧快照。当前控制revision/ledger_epoch不同则保守暂缓，不混淆为当前最新状态。
- Publish先完整检查，再追加精确响应字节和发布行；查询nonce重放只返回原持久响应或拒绝异Query。接收匹配精确Package字节，不能用同Ref的坏签名替换。纯模型业务effect元组不变，未调用任何实际工具。
- 当前代码以真实 Ed25519 验签及严格点/S/base64/编码过滤实现密码路径；Archive的完整历史合法性、受信账根/高水位、原子CAS和持久事务仍是明确外部前提。

**条件 verdict：在本轮明确的研究检查器与A1–A6范围内，未发现剩余阻止交付的 Critical/Major，历史观察恢复的机器合同已可作为局部关闭候选。** 它可以在原回执过期/原签名从未生成的情况下，由当前获批观察者认证同一受信历史接受事实；事实ID不随换观察钥变化，且不新增派发/执行/结算权。

此 verdict 的关键限制是 FrozenRead 也是受信W读取输入。真实适配器必须按 QueryRef 从受保护/持久读见证账取得它，不能将调用者上传的 FrozenRead 当权威；代码的数据类不是访问控制机制。模块/说明应将它与 Authority/History/Publication 一并列为受信输入。本轮检查器没有实现这个W读见证池，也不声称证明它的持久性。

因此可以关闭的是“在明确可信前提下，既有合法接受因旧回执签不出而无法得到当前历史观察”这一协议缺口。不能由本审查关闭真实软件的原39/66项验收、恶意W/档案丢失/独立锚缺失、无界延迟下的必然完成、或设备物理执行期限。设备端效果守卫与实时撤销协调仍按06第7节另有明确义务。
