# 协议时间补全：比较研究与推荐方案

日期：2026-10-10。模式：范围明确的比较研究；AI辅助检索、来源核对、综合与草案撰写，包含独立对抗审查。此文件是研究结果，不是完整安全证明或软件交付。

## 结论

建议保留R2“W原子接受、外部X后签回执”，先把逻辑接受、实际签署、当前观察和派发期限分清。研究分支的预签再Finalize不是原规范的等价顺序；跨整数秒拒绝属于实现限制，不能直接靠放松相等检查修复。

真正需要新增规则的是：原接受已经成立，但原回执超过冻结寿命或原钥不允补签时，怎样长期认证过去事实。候选方案是“当前受控认证者从连续W账重新认证原事实”，保持原Core/Ref/accepted_at不变，新的认证不产生执行权。该设计需要新的支撑记录、用途、类型化解析及Result附件合同，**尚未冻结为正式R3**。[补全草案](../../system_dev/v26/05_time_acceptance_recovery_PROPOSED.md)

## 问题与方法

研究问题：不依赖完整产品软件，如何使接受前时间检查、接受后外部签名延迟和长期历史认证同时拥有明确安全与恢复语义？子问题是：时间约束在哪个事件成立；签名证明过去事实还是当前许可；超时/换钥/未决提交如何恢复。

纳入：R2精确规范、已知审查、固定GitHub源码，以及直接解释时间/持久决定/签名声明的官方规范、作者论文和项目文档。排除：框架选型、前端/数据库产品实现、真实模型精度、真实物理效果与完整39项认证。检索日期为2026-10-10；关键词、章节和排除条件分别记录于[事务来源](2026-10-10-协议时间补全_事务来源.md)和[授权来源](2026-10-10-协议时间补全_授权来源.md)。这些是目的性选择的10组主源，非系统综述，未虚构全网命中数。

研究可行性：现有规范和公开主源足以比较语义并构造有限反例；价值在项目合同闭合，不主张发明新的签名算法或已证明通用新协议。完整系统性质仍需独立实现及部署证据。

## 相近协议如何处理

| 来源 | 原方案的关键处理 | 可借鉴与限制 |
|---|---|---|
| [CCF：Checking for Commit / Write Receipts](https://ccf.dev/main/use_apps/verify_tx.html) | 确定提交与收据取得分开，收据查询可能稍后才能完成 | 最接近“接受已存在、签名证据待取”；依赖其持久提交体系，不证明ZJJ已具备它 |
| [OCSP：RFC6960 §2.4](https://www.rfc-editor.org/rfc/rfc6960.html#section-2.4) | 分开状态已知正确时间、响应签署时间和更新期限 | 支持分开accepted_at与新认证iat；证书状态证明不能替代业务接受证明 |
| [Spanner §3/4.1.2](https://research.google.com/archive/spanner-osdi2012.pdf) | 可信区间配合时间戳与提交等待 | 不应把逻辑时间戳等同真实提交；commit-wait不自动证明期限前提交 |
| [Gray/Lamport §2/3](https://www.microsoft.com/en-us/research/wp-content/uploads/2004/01/consensus-on-transaction-commit.pdf) | 持久提交决定、准备后的未知与故障恢复 | 超时不证明回滚；一次签名RPC的两步也不自动构成2PC |
| [Chubby §2.4](https://www.usenix.org/legacy/events/osdi06/tech/full_papers/burrows/burrows.pdf) | 接收资源端检查sequencer，以阻止旧持锁者的迟到请求 | 只给W/X加租约不关闭实际工具的迟到窗口 |
| [RATS：RFC9334 §10](https://www.rfc-editor.org/rfc/rfc9334.html#section-10) | 比较可信时间、nonce和epoch的新鲜性方法 | 新鲜证据仍可能立即失效，需明确使用点重查 |
| [DPoP：RFC9449 §11](https://www.rfc-editor.org/rfc/rfc9449.html#section-11) | 有界新鲜窗口、请求绑定与jti重放检测 | nonce可重复；不能直接套项目一次消费或接受事务 |
| [Introspection：RFC7662 §4](https://www.rfc-editor.org/rfc/rfc7662.html#section-4) | 检查当前授权，承认缓存的撤销陈旧窗口 | active=false不能直接映射项目F（见[§2.1/2.2](https://www.rfc-editor.org/rfc/rfc7662.html#section-2.1)），查询后仍有变化窗口 |
| [TSP：RFC3161 §2.4.2/附录A](https://www.rfc-editor.org/rfc/rfc3161.html) | 给特定数据/签名字节提供带精度的存在时间证据 | 给Core打戳不证明后来才生成的X签名当时存在 |
| [CT：RFC9162 §4](https://www.rfc-editor.org/rfc/rfc9162.html#section-4) | 提前签署的承诺与随后包含证明区分 | 条件/未来声明不能冒充已完成事务证明 |

以上共同支持“明确证明对象与时间”，并不支持任意延长授权、修改旧签名时间或把超时视为未执行。2/30/120/900秒仍是本项目演示参数，来源不为这些取值背书。

## 推荐补全与验证

草案选择逻辑tg授权见证，不承诺实际提交/物理效果必须在该期限前。时间样本须覆盖本次事件，旧签名样本的年龄和不确定度不能被忽略。外部X晚于接受点签原回执是正常路径；原回执已不可补签时，新机制只认证受信任连续W账中的过去事实。

为防止扩大当前X权力，新观察机制须检查当前认证用途/范围、原资格档案、正确W提交决定、账连续性与当前请求绑定；不能让客户端给一个Core就请求“认证”。该机制继承正确W/C/X前提，不提供独立于W的历史证明。

已提供[27项抽象检查与有限状态探索](../../verification/protocol_time_closure_lab/README.md)及[22项补充协议用例](../../verification/protocol_time_closure_lab/temporal_cases.json)。抽象检查覆盖时间边界、旧样本年龄、延迟签署、原钥失效、假事实/错请求拒绝、恢复无副作用及过期不重派。完整补充用例仍NOT_RUN；原39项不改状态。
