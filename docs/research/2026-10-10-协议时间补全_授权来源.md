## 来源 1：DPoP 的证明新鲜性

Fett, D., Campbell, B., Bradley, J., Lodderstedt, T., Jones, M., & Waite, D. (2023, September). *OAuth 2.0 demonstrating proof of possession (DPoP)* (RFC 9449). RFC Editor. [全文](https://www.rfc-editor.org/rfc/rfc9449.html)。

- 原文位置：[§4.2](https://www.rfc-editor.org/rfc/rfc9449.html#section-4.2)、[§4.3](https://www.rfc-editor.org/rfc/rfc9449.html#section-4.3)、[§11.1](https://www.rfc-editor.org/rfc/rfc9449.html#section-11.1)、[§11.2](https://www.rfc-editor.org/rfc/rfc9449.html#section-11.2)。
- 原文要点：`iat` 是证明 JWT 创建时间；接收者核对请求绑定及以 `iat` 或 nonce 中服务端时间确定的新鲜窗口。窗口应有限，建议秒或分钟量级。服务端可在窗口内记住 `jti` 防重复；nonce 可以重复，仍须追踪重复 `jti`。不可预测 nonce 限制未来证明预生成。
- 质量/方法：IETF 标准中的规范要求与威胁分析，不是时限实验。
- 关联与迁移限制（研究者判断）：可作挑战、持有证明与去重分离的先例；不能把 DPoP nonce 当项目一次消费 nonce。持有证明不证明业务获准或设备事实。不能用其 `iat` 含义背书 Acceptance 的 `iat=accepted_at`；DPoP 也不提供业务事务原子性。

## 来源 2：Introspection 的现行授权与缓存代价

Richer, J. (Ed.). (2015, October). *OAuth 2.0 token introspection* (RFC 7662). RFC Editor. [全文](https://www.rfc-editor.org/rfc/rfc7662.html)。

- 原文位置：[§2](https://www.rfc-editor.org/rfc/rfc7662.html#section-2)、[§2.1](https://www.rfc-editor.org/rfc/rfc7662.html#section-2.1)、[§2.2](https://www.rfc-editor.org/rfc/rfc7662.html#section-2.2)、[§4](https://www.rfc-editor.org/rfc/rfc7662.html#section-4)。
- 原文要点：授权服务器返回 token 当前 `active` 状态；适用检查包括生效、到期、撤销、签名和资源服务器资格。缓存减少查询但可能让已撤销 token 在陈旧窗口继续使用；含 `exp` 的响应不能缓存到其后。`active=false` 还可能表示无权查询、对象不存在或状态无法确定，故不能作精确失败归因。
- 质量/方法：IETF 标准及安全性论证，无通用缓存秒数。
- 关联与迁移限制（研究者判断）：支持“签名可验仍需查当前权威状态”的思路。项目 W 内全依赖重读、接受与派发事务守卫比该标准更强；一次查询或禁用缓存仍没有消除查询后到执行前的变化。其布尔响应不能替代项目 T/F/U 的权威可知性判断。

## 来源 3：TSA 的存在证明与签名历史

Adams, C., Cain, P., Pinkas, D., & Zuccherato, R. (2001, August). *Internet X.509 public key infrastructure time-stamp protocol (TSP)* (RFC 3161). RFC Editor. [全文](https://www.rfc-editor.org/rfc/rfc3161.html)。

- 原文位置：[§1](https://www.rfc-editor.org/rfc/rfc3161.html#section-1)、[§2.1](https://www.rfc-editor.org/rfc/rfc3161.html#section-2.1)、[§2.4.2](https://www.rfc-editor.org/rfc/rfc3161.html#section-2.4.2)、[附录 A](https://www.rfc-editor.org/rfc/rfc3161.html#appendix-A)、[附录 B](https://www.rfc-editor.org/rfc/rfc3161.html#appendix-B)。
- 原文要点：可信 TSA 对数据摘要提供某时之前存在的证据；`genTime` 是 TSA 生成时间，`accuracy` 给其偏差范围。缺少 ordering 保证时，近邻时间戳不能仅凭名义时间排序。附录 A 对签名字节摘要打戳；附录 B 还需相应历史证书状态证据。
- 质量/方法：原始标准与示例；历史验证受 TSA 信任、时间和证书政策约束。
- 关联与迁移限制（研究者判断）：给冻结 Core 打戳不证明 X 签名在接受时存在；给后生成签名打戳也不能追溯其产生时间为接受时间。时间戳不授予当前授权，不证明工具现实效果，不解决原钥已失效时待签回执的恢复。项目 W 提交顺序不可直接由 TSA 时间排序替换。

## 来源 4：OCSP 分离事实时间、签署时间与新鲜期

Santesson, S., Myers, M., Ankney, R., Malpani, A., Galperin, S., & Adams, C. (2013, June). *X.509 Internet public key infrastructure online certificate status protocol—OCSP* (RFC 6960). RFC Editor. [全文](https://www.rfc-editor.org/rfc/rfc6960.html)。

- 原文位置：[§2.2](https://www.rfc-editor.org/rfc/rfc6960.html#section-2.2)、[§2.4](https://www.rfc-editor.org/rfc/rfc6960.html#section-2.4)、[§3.2](https://www.rfc-editor.org/rfc/rfc6960.html#section-3.2)、[§4.2.2.1](https://www.rfc-editor.org/rfc/rfc6960.html#section-4.2.2.1)。
- 原文要点：`thisUpdate` 是响应者最近知道状态正确的时间；`nextUpdate` 是不晚于其有新信息的时间；`producedAt` 是签署响应时间。接收要核对签名、当前响应资格及状态新鲜性。没有 `nextUpdate` 不表示永久有效。`good` 不必然证明曾签发证书或证书完整有效。
- 质量/方法：原始标准的类型语义和验收条件，没有项目业务状态保证。
- 关联与迁移限制（研究者判断）：可作为事实时间与证明签署时间分离的语义参照；它管理证书撤销状态，不管理 W 接受、资源占用或设备效果。`nextUpdate` 不保证现实状态在区间内绝不变化，`good` 也不能替代项目的角色、用途、任务与范围验证。

## 项目上下文记录（来自本地合同，并非 RFC 结论）

已只读核对 `system_dev/v26/01_core_contract.md` 的 §2.2、§3.1、§5–6：

- §2.2 将 `accepted_at` 固定为接受守卫同一可信区间的 `lo`；并发顺序以 W 提交序号确定。
- §3.1 将 Acceptance 的 `iat` 固定为 `accepted_at`，把它视为历史见证；签新回执/Result 仍须当前签署资格及时效为 T。
- §5 先在 W 接受事务冻结 COMMIT/Core 与响应账，再由 X 签冻结 Core；原钥失效/过期保持待签，不换 kid/iat/exp/ref。历史已存回执与新鲜 Result 是不同对象。
- §5–6 规定派发再查、当前查询鉴权、F/U 不推进和通信未知边界。上述四份标准均不能替这组项目合同证明安全性；尤其没有任何来源把一份冻结但尚未签名的 Core 自动转化为可验原 Acceptance。

调查限制：此注记只核对选定条款，未评估所有勘误/后继标准、完整 PKIX 长期验证配置或部署实验。若后续要定义独立签署时间、历史资格或待签恢复，应另行开展协议决策与证明，不能将本来源注记当作已批准修订。

## 追加：研究简报与候选草案的引用复核

2026-10-10 独立复核 `2026-10-10-协议时间补全_研究简报.md` 与 `05_time_acceptance_recovery_PROPOSED.md` 对上述四份 RFC 及 RFC 9334 的引用。限核对外部来源映射，不进行合同安全评审。

- 未发现三类指定混淆：简报明确 DPoP nonce 可重复；OCSP 仅作为语义参照并声明不能替代业务接受证明；TSP 明确 Core 打戳不证明后生成 X 签名当时存在。草案的新认证明确不承诺原 X sig 曾存在。
- RFC 7662 §4 对缓存撤销窗口的定位正确；`active=false` 的复合含义更精确位于 §2.1/§2.2。简报的内容正确，增加这两个定位可提高可复查性。
- RFC 9449 §11 覆盖所述内容；精确到 §11.1/§11.2 更好。RFC 3161 §2.4.2 与附录 A 定位也正确，现链接为全文入口，不属于错误引用。
- OCSP 的“状态事实时间”应读作响应者最近知道状态正确的时间，不是状态发生事件时间。现有两稿已限制为类比，没有把它当作事务提交证明；可将短语精化为“状态已知正确时间”以降低误读。
- 新增原文核对：[RFC 9334 §10](https://www.rfc-editor.org/rfc/rfc9334.html#section-10)明确状态和评估策略可在证据/结果生成后立即改变；[§10.1–10.3](https://www.rfc-editor.org/rfc/rfc9334.html#section-10.1)分别讨论可信同步时钟、nonce 与 epoch ID；[§10.4](https://www.rfc-editor.org/rfc/rfc9334.html#section-10.4)还指出 Claim 值可能早于签署很久。两稿对应引用准确。RFC 9334 是 Informational 架构文档，未定义协议 wire 格式，也未要求 ZJJ 的精确 W 使用点重查；该重查是本项目选择。

总体：就这五份 RFC 的引用语义而言，没有发现必须阻止交付的过度背书或错误定位；改善建议属于精确定位与措辞。此结论不等于新草案安全性已经证明。
