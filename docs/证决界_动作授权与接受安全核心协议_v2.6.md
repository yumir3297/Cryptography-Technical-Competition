## 1. 目标与范围

核心回答一个问题：**执行方接受的，是否正是当前有权主体批准、指定持有者提交的那个动作？**

核心包含最终动作绑定、独立执行授权、受限许可、持有证明、当前性、唯一接受和认证回执。订单真实性、历史风险检测质量、共享预算和工具最终效果分别由场景策略、权威事务和工具合同承担。协议不引入新密码原语，不保证模型判断正确或外部效果恰好一次。

采用“核心协议 + 固定场景合同 + 受信执行支撑”的结构。PAY-1为单租户订单阶段、人民币、全额付款模拟、不拆分、不批量、无多级委托。2026-10-07按开发范围另固定IND-DEMO-1与MED-DEMO-1两个合成演示Profile，分别定义严格场景合同并隔离摘要、路径和资格；规范存在不代表场景已实现。禁止通过客户端传入脚本、任意 schema 或 URL 动态扩展执行能力。

## 2. 主体与信任边界

| 主体 | 核心职责 |
|---|---|
| H 持有者 | 用登记密钥请求许可、签署最终提交、查询操作 |
| U 授权者 | 按当前角色范围对精确动作和依据签署 EXECUTE 授权 |
| G 许可签发者 | 验证依据及批准完整性，签发单次许可；不能代替 U |
| X 执行接受方 | 挑战、密码预验证、调用原子接受、签署持久结果 |
| W 权威状态服务 | 同一顺序维护当前状态、撤销、消费、接受和场景事务 |

控制管理员 C、来源 E、条件复核者 V 和派发器 A 仍存在于系统中，但不再全部作为核心交互主角。C 建立受信公钥/角色/策略登记；E 提供可认证场景证据；V 履行策略要求的复核；A 只领取已提交的执行意图。

攻击者可控制候选输入、H 客户端和网络消息，可重放、替换、并发、丢弃消息，取得公开 Permit。核心信任 C 的登记、X/W 的正确性、密钥保管、权威时间、不可绕过的工具出口。G 失陷时，不能绕过独立 U 的签名与 X/W 中固定验证器的重算；此性质不适用于 G 同时拥有修改 W、验证器或 U 私钥的权限。E 的签名不证明现实事实正确。

## 3. 动作、策略与依据

### 3.1 最终动作与上下文

`Action` 的顶层字段固定为：

```text
scope, operation_id, principal, holder, holder_kid,
executor, tool, tool_version, destination, payload
```

`scope={domain,tenant,scenario}`；标识和字节编码沿用 v2.5 §5 的限制。`payload` 由对应固定Profile schema唯一解释，不是任意扩展字典；PAY-1与工业/医疗不能互用字段。`tool/tool_version/destination` 必须等于策略中受控的工具映射，不能是用户自选网络地址。工具请求只能由已冻结的 Action 生成。

`Ctx={scope,operation_id,principal,holder,holder_kid,executor,action_hash,policy_ref,basis_ref}`。所有重复字段必须精确一致。版本与 Profile 同时进入 Action 摘要；任一动作字段改变均需新的依据、授权、许可和提交证明。

`operation_id` 由 W 受控登记，映射一个由场景确定的稳定业务意图；随机重建 ID 不产生新的业务意图。接受前可在同一意图下修订候选并重新授权；接受后冻结原 Action，不因任务或持有者更新而改写。跨版本必须共用业务意图去重账。

### 3.2 PolicyDescriptor 与 BasisRecord

`PolicyDescriptor` 是管理员批准的不可变策略记录，固定：Profile、载荷 schema 版本、验证器版本、工具映射、来源配置、任务/角色规则、复核用途、资源规则、依赖规则及有效期。`policy_ref` 为该精确记录的摘要；仅“版本名称相同”不构成匹配。激活、更换、撤销都进入 W 的单调状态顺序。

`BasisRecord` 是受控准备流程生成、由权威对象库保存的不可变依据记录：

```text
scope, operation_id, action, action_hash, policy_ref, task_ref,
evidence_refs, assessment_ref, required_reviews, deps, iat, exp
```

`required_reviews` 是固定策略导出的用途集合；`deps` 是签发前的依据依赖集合。Basis 不含 Authorization/Review/Permit，避免引用环。`assessment_ref` 指向场景计算记录；没有历史计算的未来合同必须另行定义，PAY-1 中不可为空。

Basis 本身不是第十一种核心签名消息，也不是可以信任的“检查通过证书”。action保存完整最终动作，action_hash按对应Profile重算，不能从未签提交参数补全。来源证据继续保留来源签名；U/V/G 的签名通过 basis_ref 绑定依据。X/W 必须从权威来源独立重建其依赖、计算结果及复核义务并比较。权威不可用为未知，不以客户端提供的 Basis 或缓存结论替代。

依据摘要只固定“批准了哪些输入”，不证明输入真实。客户端批准前须能授权读取并核对 Action、Basis 和相关来源；不能让人只对一个无内容展示的摘要点击批准。

### 3.3 密码与编码合同

继续采用 v2.5 §5 的 Ed25519 严格验签约定、SHA-256、受限 JCS、无重复键、禁止浮点/JSON number、十进制字符串 N、集合规范排序与大小限制。标量范围、Id、B16/B32/B64、Unicode 非空白判定不改变。TLS 1.3 与有状态请求禁用 0-RTT 仍是部署要求。

**报文结构。** 每条 Envelope 只有 `protected`、`body`、`sig` 三个顶层成员。`protected` 固定包含协议名、版本、Profile、算法、消息类型、签发者和密钥标识；取 `ZJJ-AAP / 2.6 / 固定Profile / Ed25519`，Profile只能为R2登记的三项且与scenario/路径匹配。`body` 精确为`{id,scope,iat,exp,aud,refs,deps,payload}`。签名覆盖 `protected` 和整个 `body`；缺字段、额外字段、未知类型均拒绝。

**编码与摘要。** `Enc` 表示先对值作受限 JCS 规范化，再编码为 UTF-8。下列公式规定签名输入、Envelope 引用、动作摘要及受控记录摘要；其中 `protected` 和 `body` 指同一 Envelope 的两个成员。

```text
Enc(x) = UTF8(JCS(x))
ToSign(h,b) = Enc(["ZJJ-SIG-v1",h,b])
Ref(envelope) = B64url(SHA256(Enc(["ZJJ-OBJ-v1",protected,body])))
AH(profile,action) = B64url(SHA256(Enc(["ZJJ-ACTION-v1","2.6",profile,action])))
RecordRef(profile,kind,scope,value) = B64url(SHA256(
    Enc(["ZJJ-RECORD-v1","2.6",profile,kind,scope,value])))
```

KeyID 公式不变；`version` 已进入受签名的 `protected`，不同协议版本的 Envelope 不可混用。

`RecordRef` 只标识本版受控记录，与带签名 Envelope 的 Ref 分开解析。字段定义固定预期的 `kind`，解析器不能按“哪个存储里查到了”临时选择类型。W 负责记录的来源认证、权限和持久保存；摘要本身不替代认证。

对象 `refs` 只列直接引用的 Envelope Ref。`policy_ref`、`basis_ref` 和场景记录引用按对应的受控记录解析，并受所在 Envelope 签名保护；完整分类见后端衔接文档。

时间判定仍使用 W 的 `[t_lo,t_hi]`：不确定度≤2秒，`iat≤t_lo && t_hi<exp` 才为真；明确过期为假；跨界或来源不可用为未知。依据链下游到期时间不得晚于承重上游。Permit≤120秒；Challenge/CommitProof/ChallengeRequest/StatusQuery/Result≤30秒；IssueRequest≤120秒；Review/Authorization/Acceptance≤900秒。Permit.dispatch_before=exp；Proof 不早于 Challenge 且不晚于其 exp。历史接受见证不要求重新获得执行资格。

## 4. 核心消息与接口

核心保留以下 **10 种签名消息**。相较 v2.5 的24种，这是核心规范职责的收敛，不是全系统只剩10种数据对象，也不是通信量已经下降的测量结论。

| type | 方向 | payload 设计字段及约束 |
|---|---|---|
| Review | V→U/G/X/H | ctx, purpose, verdict, reason；purpose 必须为 Basis 要求的用途；不能授予执行权 |
| Authorization | U→G/X/H | ctx, review_refs, purpose=`EXECUTE`, verdict；恰一执行授权，绑定精确复核集合 |
| IssueRequest | H→G | ctx, review_refs, authorization_ref；完整签发申请，不承担候选编辑 |
| Permit | G→H/X | ctx, review_refs, authorization_ref, max_uses=`1`, dispatch_before；权限不得大于授权 |
| ChallengeRequest | H→X | purpose, operation_id, permit_ref, action_hash, attempt_id；purpose=COMMIT或STATUS |
| Challenge | X→H | purpose, operation_id, permit_ref, action_hash, holder, holder_kid, session_id, nonce, request_ref |
| CommitProof | H→X | ctx, permit_ref, challenge_ref, session_id, nonce, attempt_id；H签名绑定该许可与该次挑战 |
| Acceptance | X→H/G/U | ctx, permit_ref, proof_ref, authorization_ref, review_refs, accept_seq, accepted_at, commit_record_ref, dispatch_before |
| Result | G/X→请求者 | request_ref, attempt_id, result, reasons, operation_id, permit_ref, acceptance_ref, status, status_seq, retry_after |
| StatusQuery | H→X | operation_id, challenge_ref, session_id, nonce, attempt_id；当前查询权限，不要求旧许可仍可执行 |

Review/Authorization 的 verdict 为 APPROVE/DENY；PAY-1 用途为 ANOMALY/LOW_EVIDENCE 与 EXECUTE，角色仍由场景合同明确区分。不得合成一个通用“批准=true”接口。

Result 新增显式 permit_ref，ISSUED 时恰好指向签发的许可，其他结果为空串；不再通过 refs 集合差推导 Permit。可空字段沿用空串表示，禁止 null/缺省。result/status 枚举沿用 v2.5 §7.3；`reasons` 沿用 Reason 结构，核心码与场景码的归属见衔接文档。ACCEPTED/EXISTING 必须有 acceptance_ref；STATUS 在存在接受时返回它。所有 Ref 都须解析并重算比对。

COMMIT 挑战的 permit_ref/action_hash 必填，STATUS 时二者为空串。请求 aud 为唯一目标服务；挑战 aud 为当前持有者；顶层响应 aud 为原请求者。依据 aud 按实际消费主体确定，至少允许对应验证方读取，不把读取权等同于授权权。Review/Authorization/Permit 的 ctx 必须一致；V/U/G/H/X 各签名用途按类型分别核验。

运输端点保持四项职责：`POST /zjj/2.6/issue`、`/challenge`、`/commit`、`/status`。继续使用规范 Bundle、原始字节限长、明确 type/path/aud 绑定及签名结果；不把 challenge 与 commit 合并成一次自动付款。后台准备、证据同步和管理更新为独立内部合同，见衔接文档，不能将其作为未经鉴权的公网端点。

## 5. 接受判定与原子合同

所有检查返回 T/F/U：有 F 拒绝，否则有 U 暂缓，全部 T 才允许接受。缺失必需字段为格式错误；准备阶段缺人工批准为 PENDING；完整提交缺必需批准为拒绝；合规引用暂不可读为暂缓。超时不是已拒绝，UNKNOWN 不能由人工批准覆盖。

核心依次要求：

1. **认证与绑定**：严格解析，核验登记密钥、用途、受众、作用域、版本、时间及全部引用；Action/ctx/Permit/Proof 精确一致。
2. **执行授权**：独立 U 的 EXECUTE 授权有效，权限覆盖 Action，绑定同一 Basis 和必要 Review；Review 不能替代它。
3. **场景合同成立**：固定验证器独立检查任务、来源和场景硬条件，重算 Assessment 与 required_reviews；所有必要复核具有对应用途、权限及主体分离。
4. **当前性完整**：W 独立构造依据、全部批准者、G/H 等资格依赖与撤销检查，和 Permit.deps 精确比较；禁止客户端选择省略依赖。
5. **持有与唯一性**：H 当前密钥匹配；挑战在 W 中存在、用途正确、未使用；操作/业务意图/许可只能接受一次。
6. **事务成立**：在同一 W 事务内重读当前状态，检查场景资源与在途约束，再原子消费许可/nonce、冻结动作、记接受、预占资源、记录派发意图和响应待签内容。

`AtomicAccept` 接收经认证请求和预验证见证，不接收 `eligible=true`。场景检查在 W 的同一快照执行；纯计算可事务外预做，但全部读取见证必须在事务中验证，新增行/空集事实也要有覆盖 revision。场景资源不足不能在已产生 Acceptance 后再补查。

接受时间沿用 v2.5 的逻辑 `tg` 与 W 顺序：取得可信时间并通过守卫后，保持事务隔离直至提交；外部按 W 提交顺序比较撤销与接受，不按客户端时间戳。事务失败整体回滚。签名失败不撤销已经持久化的接受，由待签记录恢复原回执。

同一证明精确重传返回原结果；同 session 不同证明拒绝重放。已认证拒绝/暂缓在可确定提交的响应事务内消费 nonce，但不消费 Permit、不增加接受或资源。格式/坏签名不消费 nonce。W 不可达或提交结果不明时返回通信未知，不能假造确定 DEFER。

已接受同 operation/Action 的恢复请求，在当前查询身份核验后返回原接受，不要求旧许可恢复有效；同 operation 异 Action 拒绝。业务去重账包含所有终态，不随凭据到期清除。

## 6. 接受以后

Acceptance 只证明一次接受。`commit_record_ref` 绑定 W 已提交的实际依赖、资源预占与在途见证；它替代核心消息中的人民币预算字段，明细由受控查询展示。

派发器 A 仅能从已提交 outbox 领取，按场景合同重查期限、当前资格和本操作占用后 CAS 门闩，再调用冻结工具请求。未知效果保留必要占用并停止自动重派；有权威终局才结算。状态查询不派发、不释放预算、不重新授权。

首轮仍采用 EXEC-0。EXEC-1 只有在工具另有稳定幂等键和权威查询合同并独立验收时才启用。接受唯一性、工具调用尝试、外部效果唯一性是不同性质。

## 7. 性质与证据边界

| 性质 | 本版承担范围 | 必要条件 |
|---|---|---|
| K1 无授权不接受 | 每次新接受对应独立且当时有效的 EXECUTE 授权 | 登记、签名、完整验证器及 W 正确 |
| K2 精确绑定 | 动作、主体、受众、依据和提交不可被替换 | 规范编码、摘要/签名安全、工具映射无旁路 |
| K3 当前性 | 已在 W 中撤销或变更的资格不能靠旧凭据恢复 | 完整依赖与所有写者同序；不含现实变化尚未入库的窗口 |
| K4 唯一接受 | 同一权威域内，一个稳定业务意图至多一次接受 | 服务端意图登记、跨版本去重及原子消费 |
| S1 PAY-1 业务与资源 | 订单条件、用途化复核、预算与累计次数满足 | PAY-1 验证器、来源和事务资源合同；不归因于签名单独保证 |
| S2 执行恢复 | 未知效果不自动触发重复派发 | 出口隔离、门闩和工具合同；不推出外部恰好一次 |

v2.5 P1–P4 的相关核心意图分别收敛至 K1–K3；P5 拆成 K4 与 S1；P6 属 S2；P7 资料不足复核属 PAY-1；P8 注册认证属控制平面。旧论证不能直接当作新版本证明。原“G 失陷仍不能跳过风险重算”的边界由 X/W 内的 PAY-1 验证器继续承担；若未来改为信任远程风险布尔结果，必须另改信任模型。

本版核心叙事与2026-10-07的R2精确协议合同共同构成当前规范。R2已提供三Profile Schema、协议运输结构与结构/密码向量；现有测试仅支持各自版本已测范围，完整后端、完整双实现互操作、迁移与业务攻击轨迹仍需实现验证。原软件交付顺序见[实施计划](superpowers/plans/2026-09-29-zjj-v26-backend.md)。
