# 时间、外部签名与接受事实恢复：协议补全草案

日期：2026-10-10。研究合同标识：`TIME-CLOSURE-PROPOSED-0.1`。状态：**PROPOSED，供审查；不是已冻结或实现的R3规范**。

依据为[核心精确合同](01_core_contract.md)、[R2工具终局恢复](04_tool_final_recovery.md)、[符合性补全合同](../docs/14_协议符合性补全合同.md)及[比较研究](../../docs/research/2026-10-10-协议时间补全_研究简报.md)。本稿不覆盖原合同、不改Schema或原39项验收状态。机器编码、密钥用途与响应附件兼容必须完成后才可冻结新合同。

## 1. 问题与选择

本稿处理三件事：接受前怎样使用正在流逝的时间；接受后外部签署可以延迟多久；原回执永远无法补签时怎样认证已有事实。W/C/X诚实、权威状态隔离和持久提交正确仍是前提，不研究恶意W重写全部历史或真实设备效果证明。

原R2顺序是“W原子接受并冻结COMMIT/Core，再由X签原字节”。研究分支Phase14/15/17改用“准备未来COMMIT、X先签Acceptance、W再Finalize”，并限制Prepare/Finalize的整数秒相等。跨秒合法延迟会被拒绝；同一整数秒内仍可能有非零实际延迟。预签后的控制更新也可能使Finalize失败，故不能把一份密码正确的预签Acceptance直接当成持久接受。只删除`TIME_CHANGED`不解决其事实语义。[固定源码](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/585a5f38943d8f6cb961a3005353a0d3870df744/research/phase14/verifier.py)

| 路线 | 代价与成立条件 | 本轮结论 |
|---|---|---|
| A：保留R2先接受后回执，精化时间并单独恢复历史认证 | 不在X签名等待期间占住W事务；长期恢复需要新的受控证明语义 | 推荐，以下正文采用A |
| B：真正的准备/签名/最终提交协议 | 必须区分条件签名与提交证据，重验依赖/资源/时间、持久化准备状态并解决崩溃/超时；需要新合同 | 可独立研究，不称原R2的等价实现 |
| C：等待签名期间锁住W事务，或延长全部寿命 | 锁不能停止时间，网络等待影响进展；延长寿命也不能处理永久钥失效 | 不作为本轮解决方案 |

CCF提供提交后取得收据的工程先例；OCSP的事实/签署时间区分提供语义参照；它们都不证明本项目候选安全。[CCF](https://ccf.dev/main/use_apps/verify_tx.html#write-receipts)、[OCSP §2.4](https://www.rfc-editor.org/rfc/rfc6960.html#section-2.4)

## 2. 三个时间与两个顺序

- `I_g=[lo_g,hi_g]`：W接受守卫使用的、覆盖该检查事件的当前可信时间区间。
- `accepted_at=lo_g`：原R2选择的逻辑授权接受见证；与`trusted_time`、COMMIT和原Core一起永久冻结。
- `I_s`：X实际执行回执签署或历史再认证时的当前可信区间。通常晚于`I_g`，不得要求它等于`I_g`。
- `accept_seq`及W事务序列：决定已进入W的撤销、更新与接受的先后，不能用时间戳代替。
- `durable_commit`：接受事务已不可撤销地持久提交的事件，发生后才能把接受当作已成立事实。

本稿保留**逻辑接受守卫时间**语义：合法性按`I_g`和同一W序检查，不宣称`accepted_at`等于磁盘持久化的物理时刻。隔离必须从守卫读取保持到事务决定；失败则这次候选接受从未成立。事务中途释放保护、继续使用旧快照或在X签名等待后拿旧`tg`开新事务均不属于该语义。

如果应用要求“实际磁盘提交时仍未到期”或“设备物理动作必须在期限前发生”，这是更强的不同保证，必须有能覆盖对应事件的可信区间/提交期限机制或工具端参与。普通锁、提交前再读一次时钟、Spanner式commit-wait，都不单独证明那个实际事件早于资格期限；提交后发现到期不能把已经存在的接受谎称回滚。本轮不增加该物理期限保证。[Spanner §3、§4.1.2](https://research.google.com/archive/spanner-osdi2012.pdf)

## 3. 接受前时间与当前性守卫

沿用`iat<=lo && hi<exp`才T；`lo>=exp`为F；跨界、生效前或可信时间无法确定为U。不改变2秒区间宽度、120/30/900秒等演示上限，不增设隐含宽限。

新增精化义务：

1. 时间提供者须给出**覆盖本次守卫事件**的上下界及来源/纪元/健康证据。旧C签名时间样本的签名有效，不表示它一直覆盖当前事件。
2. 若使用旧样本加本地经过时间，需要可信经过时间上下界、传输/采样年龄界限及速率误差；各误差须计入新上下界。无法界定消息单程延迟，或时钟重启/回退/来源不可用，则U，不能拿服务器收到消息后经过的时间冒充全部样本年龄。
3. 保留持久时间下界和源纪元治理，但单调下界本身不证明样本新鲜。不得重用静止在100秒的已签区间来接受现实120秒之后的过期许可。
4. 接受事务独立重建全部依赖、覆盖集合、批准、资格与资源见证；缓存密码核验结果只作预计算。任何F拒绝，无F有U暂缓，不新增接受或派发；完整协议的已认证失败响应/nonce规则仍按R2处理。

挑战nonce、版本/epoch、可信时间分别解决不同问题，互相不能替代。RFC9334特别指出，即便证据刚生成，状态/策略仍可能立即变化；因此新鲜性只给有界观察，不提供一直有效的授权。[RFC9334 §10](https://www.rfc-editor.org/rfc/rfc9334.html#section-10)

## 4. 唯一接受与外部签署

正常路径固定为：

1. W在受保护事务内全T检查，写许可/nonce消费、稳定意图、资源、Behavior/Flight、COMMIT、原Acceptance.protected/body及待签原字节，分配原accept_seq。
2. 事务持久提交成功才产生可供X认证的接受事实。提交结果不明先恢复W决定，不根据超时宣告“未接受”。
3. X通过已认证W通道读取待签条目，核对应操作、原COMMIT/完整Action、原Core/Ref、原公钥和归档资格，不签客户端上传的任意body。X不把私钥交给W。
4. 核原冻结kid的当前KEY、相应EXECUTOR角色、scope和Acceptance签署用途在本次实际签署时均为T，公钥与原冻结映射相等；原接受时的归档资格不能代替当前补签资格。原Acceptance有效期按`I_s`也为T，才可签原字节并幂等保存，不能用当前另一个kid代签。Permit现在已过期不撤销过去接受，也不必然阻止有效窗内签历史回执。
5. 延迟、失败、重复签署或响应丢失都不再接受、改Core、补占资源或重派。

**R2保留的活性边界：** 原回执冻结`iat=accepted_at`、`exp<=accepted_at+900`，实际可补签窗可能更短。原钥永久不可用/撤销或回执到期时，R2不保证原Envelope最终可生成。保留这一限制是保守安全选择；若要求客户端长期能认证过去接受，才需第5节的新机制。

## 5. 候选：当前认证原接受事实

### 5.1 不可变事实与可更新认证

候选支撑记录暂称`ACCEPTANCE_OBSERVATION`。它与原Acceptance不同，不是新增的接受授权；名字、编码、字段枚举尚未成为原R2 wire合同。

不可变接受事实候选字段：

```text
AcceptanceFact = {
  profile, scope, operation_id, action_hash,
  ledger_origin, accept_seq, accepted_at,
  commit_record_ref, original_acceptance_ref, original_core_digest
}
AcceptanceFactID = SHA256(Enc(["ZJJ-ACCEPT-FACT-PROPOSED-v1", AcceptanceFact]))
```

`original_acceptance_ref`始终是原protected/body计算出的原Ref，即使原sig从未生成也不能改写。原Core、COMMIT、Action和当时资格档案必须保留；该摘要不能反向证明档案的正确性。`original_core_digest`承诺归档的完整原Core规范字节，采用与原Ref不同的显式域。

新认证候选字段至少包含：完整AcceptanceFact及FactID、当前认证issuer/kid/用途与scope、认证iat/exp、当前请求Ref/挑战关联、W历史来源/连续性见证引用；签名覆盖全部。认证iat来自现在，原accepted_at仍来自过去。新RecordRef不改原Ref，不承诺原X sig曾存在。

### 5.2 新认证成立条件

必须同时满足：

1. 请求者当前查询身份/范围为T，使用有效的新StatusQuery，或合同明确允许的当前EXISTING观察请求。
2. 当前认证X的KEY、ROLE、scope与明确的**历史事实认证用途**为T。当前EXECUTOR角色或READ资格不能未经新合同自动视为这个新用途。
3. X从其认证的W权威历史入口读取原已提交记录；归档全部字段可重算，原接受时资格、检查见证、事务决定与稳定意图可核验。不能从客户端Core、原sig为空或一个摘要推断合法接受。
4. C批准的同一W账身份和根代移交/恢复链连续，原序号/永久墓碑未回退、未分叉，记录属于受信任的连续历史。相同`ledger_origin`字符串不构成连续性证明；新库不能认证旧库未决事实。
5. 认证时间及当前资格为T，新认证寿命不超过新请求窗口和当前资格的有效期。不得把旧Permit/旧业务授权重新设为有效。
6. 接收端重验签名、当前认证映射、scope/请求绑定、原事实全部字段和来源证据；一次密码验签不能代替这些条件。

该机制把恢复信任放在正确W历史、当前受控X/C及连续账上，**不提供独立于W的第三方历史安全证明**。恶意W、失去档案、未知的备份连续性或原事实来源无法证实时，不签成功认证。若已知有接受但缺证明，维持“响应待恢复/通信未知”，不能伪造REJECT表示从未接受。

### 5.3 无副作用与失败语义

认证可以重复；新接受/许可消费/资源预占/执行/结算次数均增加0。允许持久保存观察审计记录，但不更改原操作决定和效果账。

旧业务资格已撤销，不妨碍正确认证过去合法事实；当前认证者资格撤销则阻止**这次新认证**。原签名可能在过去已失陷或历史合法性不可判定时，不仅凭原密码签名给确定结论。

同一事实新认证不产生矛盾；经认证且同绑定下的不同事实为完整性事件，按受控停止规则处理，不能择一改账或重新执行。匿名垃圾/错绑定包不得使合法操作自动HALTED。

## 6. STATUS、EXISTING与兼容规则

原R2成功响应要求可验原Acceptance。新认证不能在仍执行原验证规则的客户端中冒充它。

候选新合同要明确成功响应可引用原接受身份，并附下列二者之一：

- 原完整Acceptance，由归档资格作历史验证；或
- 新`ACCEPTANCE_OBSERVATION`＋所需原Core/COMMIT与认证历史见证，按新合同验证。

当前STATUS的status/status_seq仍来自本次W只读快照；过去存在接受不等于现在仍为ACCEPTED，可能已取消、成功、未知或HALTED。Proof只认证过去的事实，不能覆盖当前状态。

附件解析必须增加“原Core归档身份”这一明确类型，不能把没有sig的Core存成一个假的Envelope，或按摘要在任意库里试解析。原RecordRef/EnvelopeRef算法不变，但解析/可接受附件集合发生变化，必须显式版本隔离。

原请求精确重传只返回**已经持久保存的原完整响应**，不为它改iat/status或偷偷补成新结果。原完整响应尚未生成时，继续按原合同保持待恢复/通信未知，不凭重传制造新响应或谎报从未接受。需要新鲜认证时发新挑战/查询；旧过期请求不能被当作新当前授权。当前有效提交在独立查询鉴权后发现既有接受，可按新合同返回EXISTING及历史认证，无第二次接受。

新kind、新认证用途、历史来源格式、Result附件选择、类型化Ref解析、错误与迁移需一起落实Schema/OpenAPI/独立向量；**在这些产物冻结前，本稿不得被实施者称为正式R2兼容处理器。** 本轮只保留研究级语义定义，不生成“已冻结R3”标识。

## 7. 派发期限与工具恢复

新鲜历史认证不能延长`dispatch_before`，不能恢复许可/nonce消费或intent墓碑。领取事务仍使用当前可信区间和非自变依赖；F且确认pending可按原合同取消自身占用，U保留，started后不重派、不自动释放。

例如：100秒接受，120秒派发截止，1100秒才取得新历史认证。可证明100秒接受过，但不能因此在1100秒执行原动作。已started的丢响应仍只能查询/认证原attempt，工具终局沿用R2的原FinalFactID、连续账和一次结算。

领取至实际发送/物理动作的撤销窗口仍是R2明示边界。Chubby式sequencer由资源端检查才有用；只在W或X本地加租约不关闭该窗口。不把内部传输重发擅自解释为EXEC-0允许的第二次应用层执行。[Chubby §2.4](https://www.usenix.org/legacy/events/osdi06/tech/full_papers/burrows/burrows.pdf)

## 8. 需要验证的不变式与有条件进展

| ID | 性质 |
|---|---|
| I1 | 仅在接受守卫全T、W事务持久成立后有一次接受；预签/准备记录不构成事实 |
| I2 | 原Action/Core/Ref/accepted_at/accept_seq永久不变，恢复不新增接受 |
| I3 | 新鲜认证时间不替换事实时间，不重新授予派发权 |
| I4 | 原过期/撤销对象不能用于新接受；历史签名验证与新认证资格分开 |
| I5 | U不能推进接受/领取或释放started占用，超时不等于确定回滚 |
| I6 | 当前认证绑定当前请求和权威连续历史，不能认证客户端选择的假事实 |
| I7 | started不回pending；终局/结算继续按原attempt唯一 |

可完成条件P1：必须存在一次实际签署区间`I_s`，原回执及原钥签署资格在该区间均为T，并在这个有效机会内完成认证读取与签署，随后可持久保存并历史核验原签名字节。仅“服务最终可达”不足：若直到原exp之后才可达，就没有原回执补签机会。

可完成条件P2：连续W档案与当前合法认证者可取，且一次新查询的身份、时间、读取/签署和响应验证能在各自有效窗口内完成，则可取得新历史认证。无界通信延迟即使最终送达也可能让每次证明都过期；不能承诺必然完成。

P1/P2是候选的完成前提，不是本轮已经证明的公平调度或长期活性定理。永久网络故障、C/X恶意、账丢失或档案损坏仍不保证恢复。
