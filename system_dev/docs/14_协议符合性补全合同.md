依据：[核心协议 §3–§6](../../docs/证决界_动作授权与接受安全核心协议_v2.6.md)、[后端衔接 §4–§5](07_v2.6_协议瘦身与后端衔接.md)、[旧参考实现审计 D04/D05/D06](02_源码审计与差异.md)。本文细化符合性要求；实验研究实现与完整 v2.6 服务的覆盖范围必须分别报告。

## 1. 三项补全的责任边界

| 义务 | 必须由谁执行 | 核心正文保留的规则 | 本文展开的内容 |
|---|---|---|---|
| 完整依赖 | 固定场景验证器及 W | 验证方独立重建，Permit 不得漏项 | 根对象、隐式依赖、闭包、冲突及事务见证 |
| 认证回执 | W 冻结事实，X 签固定内容 | Acceptance 对应唯一持久接受，可恢复 | 保存顺序、签名失败、历史核验与引用稳定性 |

## 2. 独立重建完整依赖

### 2.1 输入必须有独立来源

`BuildRequiredDeps(Action, Policy, Basis, Approvals, Snapshot)` 的 `Snapshot` 是 W 的同一受保护快照。Action 是已解析并核验 AH 的准确对象；Policy 来自当前激活行；Basis 通过指定 kind 的权威对象库读取；Approvals 是已验签、核对用途和绑定关系的 Review/Authorization。

客户端可提交引用和缓存副本，但不能提交可信的 `required_deps`、`eligible=true`、风险结论或资源预占数。G 签出的 Permit.deps 是待比对的声明，不是构造依赖的唯一输入。预登记一份客户端清单，再逐字比较同一清单，不算独立重建。

### 2.2 确定根对象及关系

1. 由 Action.scope 定位当前 POLICY，核对精确 policy_ref、Profile、schema/验证器版本及工具映射。
2. 由受控 operation/稳定业务意图定位 Task、订单阶段和付款主体，核对 Basis.task_ref 与 Action 的一致性。
3. 按固定 PAY-1 合同解析来源 Evidence、经验分区与 Assessment 输入，验证签名、scope、当前对象引用和承重字段。
4. 在该快照重算 Assessment 与 required_reviews，再检查恰当用途的 Review 集合，以及独立 EXECUTE Authorization。检查 U/V 的登记主体分离，不能仅比较 kid。
5. 对全部资格依据的签名者，以及 G/H，加载其 KEY/业务 ROLE 和资格依据。X/Challenge/CommitProof 的会话认证另作当前检查；不把尚不存在的会话对象反向加入签发前 Basis。
6. 区分承重资格边和历史出处边。历史注册挑战等已过期出处不参与当前资格的到期继承，避免无限递归或无理由失效。

必须重算每个 Ref/RecordRef 并核对预期类型，不使用“哪个库查到了就按哪个类型解释”。图限制仍按衔接文档执行：深度≤16、依赖≤256、对象≤64 KiB、Bundle≤1 MiB/128对象；循环、错误 kind、越界拒绝。

### 2.3 依赖集合的构造与比对

设 `D_implicit` 为固定验证器从动作、策略和已验证资格图导出的当前行，`D_declared` 为该图中承重对象声明的传递依赖。计算：

```text
D_required = Normalize(D_implicit ∪ D_declared)
Permit.deps 必须精确等于 D_required
```

`Normalize` 按固定规范编码排序，按 `(namespace, full_key)` 合并。同一键出现不同 revision 或 ref 为 DEP_CONFLICT；规范集合中的重复项、额外依赖、缺失依赖均不能通过。集合相等后，还须逐项核对当前行的 scope、active、revision、ref，并查询适用的对象撤销状态。

| 当前行 | 独立定位来源 | 必须覆盖 |
|---|---|---|
| POLICY | Action.scope | 精确策略记录、验证器与工具映射 |
| TASK | 权威操作登记及 Basis.task_ref | 主体、持有者、阶段、授权范围、当前任务 |
| ORDER | Action 的稳定订单阶段与付款主体 | 金额/收款方/验收/未结算/收款资格及其覆盖版本 |
| EXPERIENCE | POLICY 的固定经验分区 | 所选案例以及未选中/新增案例可能改变选择的事实 |
| KEY/ROLE | 已认证来源与批准者，以及 G/H | 登记主体、用途、scope、额度/工具范围、有效期与撤销 |
| BEHAVIOR | Action.principal | 接受前累计与在途规则；派发阶段按第4节换用自身占用见证 |

实际组合键继续沿用已确认的 namespace 合同；不可只用显示名称拼接替代完整 scope。预算不固定签发时余额：资源键及预占量由 Action 导出，在接受事务内重读容量与现有预占。

### 2.4 空集与新增行也要有见证

“没有另一笔在途操作”“尚无验收撤回记录”“这些是截至 cutoff 的全部候选案例”都是读取事实。它们须由范围覆盖 revision、单调分区版本、唯一约束或等价的事务冲突保护覆盖。只核对已存在对象的 Ref，不能发现新插入的承重记录。

纯签名检查和确定计算可在事务外完成，但必须保存所有输入的版本/范围见证；W 接受事务重新核验。任一承重变化使旧见证失效，重新准备与授权，禁止就地修改已签 Basis 或偷偷删除失效依赖。

### 2.5 失败规则

已确认的漏项、冲突、错误绑定、无权主体、硬事实为假或已撤销为 F；临时不可读的合法引用、时间跨界、权威不可用为 U。完整提交缺少必需批准为拒绝，准备阶段尚待人工签署为 PENDING。独立授权不能把 U 变成 T。

F/U 的响应只有在相应事务提交可确定时才能持久登记；已认证请求按原规范消费 nonce，Permit、接受数和资源保持不变。状态服务不可达或事务结果不明时属于通信未知，不能假造已经持久化的 DEFER。

## 3. 固定 Acceptance 内容并恢复原回执

### 3.1 同一接受事务中的顺序

```text
完整守卫成功
→ 固定 Action、实际 checked_deps、资源前后及在途见证
→ 分配 accept_seq，保存 COMMIT（不含 acceptance_ref）
→ 计算 commit_record_ref
→ 固定 Acceptance.protected 与 body（含 commit_record_ref）
→ 计算 Ref(该 protected/body)，保存待签原字节及 signing_kid
→ 同事务写入消费、预占、意图去重、outbox、接受与日志
→ 持久提交成功
→ X 签保存的原字节，验证并保存完整 Envelope
```

这里的 Ref 算法继续不含 sig；这允许接受事务提前固定真正的对象引用，不允许把任意内部 ACK 摘要当成 Acceptance Ref。COMMIT 不引用 Acceptance，避免摘要环。

待签记录至少包含原 `protected/body`、ToSign 原字节或可准确重建它们的规范字节、signing_kid、acceptance_ref、所属操作和状态。签名者只签受控待签记录，不能接受客户端任意待签 body。保存签名后须再次核对签名、Ref 和原 Core 一致。

### 3.2 故障与重试

| 故障位置 | 可确定事实 | 恢复动作 |
|---|---|---|
| 接受事务提交前失败 | 未接受，全部写入回滚 | 依正常提交语义重试 |
| 接受已提交、签名暂不可用 | 接受已存在，回执待签 | 读取原待签字节，重试签名；不新增接受/预占 |
| 签名已生成、保存失败 | 接受已存在，签名发布未确认 | 对原 Core 恢复并验证；签名保存以原 Ref 幂等 |
| 已保存回执、网络响应丢失 | 原完整回执存在 | 当前身份鉴权后返回原回执 |
| 原签名密钥不可用或不再允许签署 | 接受事实仍存在 | 保留待恢复/停止发布状态并报告；不得换 kid 重建原回执 |

签名恢复绝不把接受事实撤销，也不重新执行工具。未签的 Core 只能作为内部持久事实或受控展示数据，不能作为已经认证的 Acceptance 对外验收。

如果原密钥已销毁、撤销或签名政策不允许补签，现合同不保证回执最终可恢复。引入新密钥认证旧事实需要单独的历史见证规则；不可悄悄更新原 protected、iat、exp、accept_seq 或 Ref 来掩盖问题。

### 3.3 历史事实与当前资格

历史 Acceptance 证明在原接受点发生过接受；它不因 Permit 现在过期而需要重新授权。历史核验需要保留原公钥、当时的资格/密钥见证、原 Core 和 COMMIT，不能简单要求签名者今天仍具有执行权限。

状态查询仍核验查询者的当前权限，并绑定当前请求和 status_seq；旧 Acceptance 不能充当新鲜 STATUS。历史签名的密码有效性与接受见证的可信性也是两层判断：若发现密钥可能在接受前已失陷，单纯“签名能验过”不能证明授权事件可信。

## 4. 派发领取时重查

### 4.1 检查与门闩必须同事务

`ClaimDispatch(scope, operation_id, trusted_time)` 仅操作已接受、outbox 为 pending 的冻结动作。领取事务须检查：

1. 时间区间有效，`t_hi < dispatch_before`；跨界或时钟不可用为未知，不能用客户端时间替代。
2. 当前任务、角色、密钥、来源、策略、经验及工具映射仍与承重见证相符；包含适用对象撤销。
3. 本操作的 reservation 明细仍归属于它，数额/资源键正确；TaskFlight 指向它；Behavior.inflight 包含它，累计和容量约束成立。
4. 对接受时本操作必然改变的 BEHAVIOR，不比较 Permit 中旧 revision；使用 COMMIT 的接受后见证及当前自身占用，其他承重行不能豁免。
5. 成功才 CAS `pending → started`，保存唯一 dispatch_attempt 与冻结工具请求。领取提交后才能调用工具。

`started` 是已经领取派发权的事实，不是工具已成功执行的事实。W 的判定保证截至领取事务的序列点；不能将其写成“任何撤销只要在真实网络发送前发生都能拦截”。领取后的调度/网络间隙若也要阻止效果，需工具参与验证执行凭据、期限及撤销，这是另一个工具合同。

### 4.2 取消、未知与资源处理

| 情形 | 处理 | 资源与去重 |
|---|---|---|
| pending，确定已过期或资格失效，CAS 证明尚未被领取 | 同事务转 FAILED_CONFIRMED，记录取消原因 | 只释放本操作可释放占用；接受、累计次数、意图/Permit消费墓碑保留 |
| pending，资格/时间/权威状态未知 | 暂缓领取 | 不调用工具、不释放占用，不声称确认未生效 |
| 已 started，响应丢失或恢复时无法判定是否发出 | EFFECT_UNKNOWN，EXEC-0 禁止自动重派 | 保留必要预占与在途 |
| 权威工具确认本操作已成功 | 原终局幂等结算 | 一次预占转支出，一次释放在途 |
| 权威工具确认本操作未生效且不会迟到生效 | FAILED_CONFIRMED | 一次释放可释放占用；保留去重 |
| 相互矛盾的终局、占用账不一致 | HALTED，交由受控恢复 | 不凭猜测返还资源或重发 |

派发门闩和取消使用同一 W 写者顺序。取消只适用于尚未领取的 pending；不能看到“当前工具查不到记录”就取消已 started 操作。工具终局必须绑定 scope、operation、AH、dispatch_attempt，不能用别的请求的成功响应结算。

## 5. 可验证的验收要求

以下为完整系统的义务清单，不能因为局部实验通过就整表标为 PASS。

| 编号 | 对抗/故障输入 | 必须观察 |
|---|---|---|
| C01 | G 对删除任意一个承重依赖的 Permit 重新合法签名 | X/W 独立重建检出；0接受/预占 |
| C02 | 修改风险结论、复核用途或删除 EXECUTE | 依固定场景重算/独立授权拒绝，G不能代替U |
| C03 | 已读范围新增一条承重记录或空集变非空 | 覆盖revision使旧依据/预验证见证失效 |
| C04 | 以合法签名替换scope、Action、Basis或对象kind | 绑定错误拒绝；不误判成另一个合法动作 |
| C05 | 提交前故障 | nonce/Permit/接受/预占/outbox全部回滚 |
| C06 | 接受后签名失败、重启、重复恢复 | 原Core/Ref不变；一次接受/预占；完整回执可验 |
| C07 | 原签名密钥不可用、换钥请求恢复 | 不换kid伪造原回执，不再次接受 |
| C08 | 接受后、领取前撤销或改变承重行 | pending确定失效时取消，无工具调用，释放正确操作占用 |
| C09 | 期限跨界/当前性未知，与明确到期对照 | 未知保留；明确失效可取消；均不发送 |
| C10 | 接受改变自己的Behavior | 正常领取不自我失效；删自身reservation/flight必须拦截 |
| C11 | 8路提交、8路派发、撤销/领取竞争 | 至多一次接受/领取/EXEC-0调用，顺序可解释 |
| C12 | started后宕机/超时、矛盾终局 | 不自动重派；未知保留占用；矛盾停止 |

每次运行保存 profile/build、输入及源码散列、原始日志、真实签名、W序号、接受/派发/工具计数与资源前后账。测试桩或固定研究场景的通过，只支持其明确覆盖的性质。
