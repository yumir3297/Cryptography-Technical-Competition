# 协议架构图审查与重绘规范

> 用途：国赛 PPT 整体架构图、开发级流程图修改及验收。  
> 审查对象：现有 L0–L5 纵向流程图。  
> 源码基线：`yumir3297/Cryptography-Technical-Competition`，`main` 审查快照 `e9b3cfe92deba1274810d161c561fb8039189044`（2026-11-24 对话中核验）。  
> 所有源码链接固定到上述提交，避免后续提交造成行号漂移。

## 1. 总体结论与修改原则

原图基本覆盖了当前代码的主要运行流程，并已纳入 GoalFloor，但仍需修正事务边界、执行资格、核验时序和义务状态反馈。作为开发调用图可继续完善；作为答辩主图，不能让函数名和异常分支掩盖协议机制。

- **开发级图**：保留原 L0–L5 编排，逐项修正下述逻辑错误，显示必要状态、失败分支及代码定位。
- **答辩级图**：以 Agent → 受信安全控制层 → 工具效果端为主轴，用一个新约束、一个新关系、一种统一机制组织视觉重点。
- 图中严格区分四种关系：业务控制流、密码学证据绑定、事务边界、跨动作状态反馈。不得将四种关系混为同一种箭头。
- 统一规范依据：[统一协议正文](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/docs/final/competition-protocol.md)；当前研究结论：[研究状态](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/RESEARCH-STATUS-20261124.md)；创新定位：[核心贡献](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/evaluation/core-contributions.md)。

## 2. 必须修正的逻辑错误（按优先级）

### P0-01：C 与 W 的持久化事务边界

- **原图问题**：L5 将 P1 W SQLite 和 P2 C 登记库画成两个独立数据库，容易误解为两个独立事务域。
- **修改动作**：用一个共享 SQLite 容器包住 C 控制状态（`a_current`、`a_journal`、`a_publication` 等）与 W 业务状态（`w_operation`、`w_resource`、`w_reservation`、`w_goal` 等）。标明 `BEGIN IMMEDIATE`；工具效果端 SQLite 另画，不能纳入同一个数据库事务。
- **应强调的价值**：控制状态与接受账本处于共同事务序列，约束读取、资源预留和接受记录能够在统一边界内完成。
- **源码定位**：[TrustedState 初始化及 tx](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/trusted_state.py#L39-L75)；[CommonW 表结构及共享 state](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L26-L67)；[本地运行时装配](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/application/local_runtime.py#L150-L171)；[协议 §4.1](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/docs/final/competition-protocol.md#L157-L196)。
- **验收**：图上只有一个 C/W 共享物理库；工具账本独立；原子事务不跨越外部工具调用。

### P0-02：COMMIT 与 X 签署回执之间的执行门

- **原图问题**：`COMMITTED / receipt PENDING` 直接通向 worker/CLAIM，容易误解为未签回执即可领取执行资格。
- **修改动作**：COMMIT 持久化 → 冻结 Acceptance Core → X 签署并验证 → 保存合法回执 → CLAIM。签署失败进入 receipt pending，保留接受事实与资源占用，只允许恢复原 Core；不得成功新领取。
- **精确边界**：worker 挑战可先发起；禁止的是无合法回执的新 CLAIM 成功，而非禁止挑战请求。
- **源码定位**：[accept / COMMIT](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L284-L344)；[complete_receipt](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L347-L363)；[签名进程核验原提交](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_receipt.py#L81-L114)；[worker 挑战与认证](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L364-L378)；[claim](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L408-L421)。
- **验收**：回执未签分支不会产生新 attempt；签署恢复返回原回执，不重新接受或重新预留。

### P0-03：CommonGuard 不是一次性前置检查

- **原图问题**：L1 的 CommonGuard 仅表现为 ACCEPT 之前的一次授权核验。
- **修改动作**：将其画成 W 的共享验证组件，明确 PREPARE 初检、ACCEPT 事务内重核及最终时间窗口重核。CLAIM 单独体现当前依赖、批准/否决、身份资格、窗口和归属的相应重核；EXECUTE 与 SETTLE 各有阶段专用守卫。
- **不能误画**：CLAIM 并非再次完整调用 `CommonGuard.verify`，而是 `_claim_checks` 利用 CommonGuard/适配器及冻结状态重建相应条件；GoalFloor 也不是每个阶段都重新计算。
- **源码定位**：[CommonGuard 核验](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/authorization.py#L9-L85)；[prepare / challenge_accept](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L257-L283)；[accept](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L284-L344)；[领取阶段重核](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L395-L421)；[执行与查询守卫](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L434-L472)；[终局与结算守卫](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L473-L521)；[可信时间与窗口](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/event_clock.py#L20-L57)。
- **验收**：图上能读出 PREPARE 成功不等于 ACCEPT，ACCEPT 成功不等于已领取执行资格；各阶段的检查范围不被混同。

### P0-04：GoalFloor 缺少义务状态闭环

- **原图问题**：GoalFloor 只有判定节点，没有结算结果反向影响后续接受的路径。
- **修改动作**：增加 W 资源账本与义务状态账本到 GoalFloor 的输入；接受形成 PENDING，可信成功结算形成 DONE，可信确认失败或合法取消形成 BLOCKED；状态及资源变化回流至下一次候选动作的 GoalFloor 判定。
- **关键限制**：UNKNOWN、待回执及未决效果不能被当成 DONE；PENDING 保留占用。在 enforce 模式下，适用资源上的 PENDING 或 BLOCKED 会阻断新接受。停用仍有 PENDING 的 Goal 具有额外的 Profile 级阻断条件。
- **源码定位**：[evaluate 与状态摘要](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/goal_floor.py#L111-L209)；[Goal 状态加载、上下文及见证](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L131-L243)；[接受与 PENDING 关联](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L320-L344)；[取消与 BLOCKED](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L422-L433)；[结算与资源更新](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L501-L527)；[协议 §3.4](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/docs/final/competition-protocol.md#L118-L132)。
- **验收**：每个义务状态都有来源；UNKNOWN 无释放占用或完成义务的箭头；反馈明确指向下一次 ACCEPT。

### P0-05：GoalFloor 模式与约束适用条件

- **原图问题**：未清晰区分 off、shadow、enforce，可能把所有运行入口都表述为强制保护目标必要资源。
- **修改动作**：在 W 受信配置旁标明 off（不计算）、shadow（计算并记录但不以该拒绝阻断）、enforce（适用约束必须为 T）。无适用约束时仍按原守卫判定；控制加载失败等保守阻断条件不能被误当作不适用。
- **源码定位**：[模式配置及唯一索引](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L26-L58)；[适用条件与见证](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L165-L243)；[接受事务中的模式判定](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L284-L344)；[协议 §3.5–3.6](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/docs/final/competition-protocol.md#L133-L148)。
- **验收**：答辩主图若突出 GoalFloor，应标注「enforce + 适用的 C 认证约束」；不得将默认 off 入口宣称为已强制启用。

### P1-06：补全可信动作构造、编排与请求版本

- **原图问题**：Agent 意图到授权门之间缺少完整 Action 的形成过程。
- **修改动作**：增加「候选意图 → 可信构造 → 完整 Action / ActionHash → Basis / Assessment / RequiredDeps → 授权链」；表示请求冻结及版本绑定属于可选应用路径的实现约束，CommonGuard 仍独立重算受信依据。
- **源码定位**：[Server 提交与完整 Action 构造](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/server/service.py#L91-L131)；[TrustedActionResolver](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/application/trusted_action_resolver.py#L20-L130)；[候选提案结构](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/application/candidate_proposal.py)；[受信编排](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/application/operation_orchestrator.py#L10-L90)；[请求冻结、替换及当前性](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/application/request_store.py#L86-L160)；[请求绑定 W](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/application/request_bound_w.py)；[独立重算和绑定核验](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/authorization.py#L35-L85)。
- **验收**：Agent 只提供候选数据，不自定权限、必要复核、依赖或目标义务状态。

### P1-07：补全 E 来源认证角色

- **原图问题**：控制层未独立表达 E 对来源事实的认证。
- **修改动作**：E → 签名来源事实 → 可信构造及 CommonGuard 重算。C 负责登记和发布控制约束；E 负责来源认证；二者不能混同。
- **源码定位**：[场景来源核验与 derive](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/profiles/authorization_scene.py#L19-L127)；[支付来源核验与 derive](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/profiles/authorization_pay.py#L31-L149)；[当前控制记录、资格及读取权限](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/trusted_state.py#L164-L197)；[协议角色与动作承诺](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/docs/final/competition-protocol.md#L19-L37)。
- **验收**：注明签名认证的是来源及内容，不自动证明现实事实为真。

### P1-08：限定 CANCEL 的语义

- **原图问题**：取消容易被理解为任意时刻可撤销或回滚已执行动作。
- **修改动作**：CANCEL 从尚处 PENDING、尚未领取且满足已知失效条件的分支引出；释放资源、保留接受意图墓碑、关联义务转为 BLOCKED。STARTED 不允许通用取消。
- **源码定位**：[cancel](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L422-L433)；[_release](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L522-L527)；[协议 §6](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/docs/final/competition-protocol.md#L221-L232)。
- **验收**：不存在从 STARTED/UNKNOWN 随意取消并释放占用的路径。

### P1-09：QUERY 与 EXEC-0 必须分离

- **原图问题**：查询恢复可能被误解为重新执行原请求。
- **修改动作**：CLAIM 固定唯一 attempt；EXEC-0 先消费持久执行标记再派发；重复执行返回 `EXEC_ALREADY_CONSUMED`，只能通过 QUERY 认证原 attempt 的事实。未知结果保留资源；可信矛盾进入 HALTED；有效终局进入一次结算。
- **源码定位**：[唯一 attempt 与 W 签名派发包](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L408-L421)；[EXEC/QUERY](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L434-L472)；[工具验签、执行与查询](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/tools/common_tool.py#L164-L250)；[终局核验及一次结算](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L473-L521)。
- **验收**：QUERY 无新增 attempt 或重复效果的箭头；不得将一次执行资格扩大解释为保证实际效果恰好一次。

### P1-10：区分 Server 演示入口与 HTTP/MCP 应用路径

- **原图问题**：可能将所有入口及应用模块画成同一条必经链路。
- **修改动作**：Server 演示入口和可选 IND HTTP/MCP 应用入口分别画成适配路径，汇入 CommonW 核心机制；MCP stdio 适配本地 REST，不应标注为 MCP Streamable HTTP。
- **源码定位**：[Server submit/challenge/prove](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/server/service.py#L91-L174)；[可选 IND 应用入口范围](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/application/README.md)；[REST 入口](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/application/http_service.py)；[MCP stdio 适配](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/application/mcp_stdio.py#L35-L106)；[应用方法分发](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/application/operation_service.py#L84-L116)；[本地装配](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/application/local_runtime.py#L128-L171)。
- **验收**：不同入口不是串联的唯一调用链；公开 Agent 接口与受信 worker、签名角色职责分离。

## 4. 三个核心卖点的独立表达

### 4.1 一个新约束：目标必要资源下界（建议橙色）

**问题**：传统局部动作门控即便逐步合法，也可能逐渐消耗后续必要事项所需的资源。

**机制**：C 发布签名认证的 GOAL_FLOOR；W 使用冻结 Action 的 Selector 匹配义务，从资源账本获取权威成本，并读取当前义务状态。在 enforce 且约束适用时，接受必须满足：

$$S+R+c(A)+F(A)\leq K$$

- S：已消耗；R：已预留；c(A)：W 计算的候选动作成本；K：认证容量。
- F(A)：同一资源域的剩余 OPEN 必要事项成本保守求和，排除本次已匹配义务，避免重复计入候选成本。
- Selector 不含 operation_id，ActionHash 则承诺完整 Action；两者职责不同。
- 状态 `OPEN → PENDING → DONE/BLOCKED` 与资源账本形成反馈。未知不等于完成；PENDING 保留占用。

```text
C 认证 GOAL_FLOOR / revision / deps ───────┐
冻结 Action → Selector / 候选成本 ────────┼──→ W 联合判定 → 原子 ACCEPT
资源账 + 义务账 ─────────────────────────┘         │
       ↑                                           ↓
       └──────── 结算 / 合法取消更新状态 ←── 执行与终局
```

**卖点表述**：从单步动作合法性检查，扩展到连续自主动作下的目标必要资源保护。

**源码与证据**：[核心算法](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/goal_floor.py#L40-L209)；[状态及 W 见证](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L131-L243)；[原子集成](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L284-L344)；[规范 §3.1–3.6](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/docs/final/competition-protocol.md#L59-L148)；[规则消融对照](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/evaluation/baseline_comparison.md)；[长序列实验](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/evaluation/experiments/long_sequence.py)；[资源下界余量图](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/evaluation/figures/fig2-goal-floor-margin.png)。

**边界**：该机制保护已认证的必要资源条件，不证明目标可达、计划正确、路径最优或任务最终成功，也不宣称已经对所有竞品进行直接对照实验。

### 4.2 一个新关系：动作生命周期中的密码学证据绑定（建议蓝色）

**问题**：单条消息验签通过，不意味着跨角色、跨时间、跨阶段的依据、授权和执行对象一致。

**机制**：通过规范化编码、域分离、SHA-256 承诺、Ed25519 签名和对象引用形成可核验关系图。图中应画出证据依赖，而不是暗示所有节点都直接签署上一节点或组成线性哈希链。

```text
完整 Action → ActionHash ──→ Ctx / Basis / Assessment
                              │
                    Review / Authorization / Permit
                              │
                     Challenge / CommitProof
                              ↓
              COMMIT（含适用的 Goal Witness）
                              │ RecordRef
                              ↓
                       X Acceptance
                              │ Acceptance Ref + Commit Ref
                              ↓
                  W 签名派发包 + 唯一 attempt
                              │ ActionHash / attempt / request
                              ↓
                    TOOL_FINAL + Checkpoint
                              │ FinalFactID
                              ↓
                           SETTLE
```

| 组件 | 应体现的作用 | 源码定位 |
|---|---|---|
| SHA-256 与规范化编码 | 形成内容承诺、稳定 ActionHash、MsgRef、RecordRef | [canonical / digest / refs](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/support/wire.py#L58-L104) |
| Ed25519 | 认证各登记角色签发的消息，验证持钥和签名 | [strict_verify / envelope](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/support/wire.py#L141-L188)；[签名调用约束](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/signer_broker.py#L29-L90) |
| Ctx / RequiredDeps | 将动作、策略、依据、复核及授权绑定，并独立重算依赖 | [授权关系核验](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/authorization.py#L35-L85) |
| COMMIT → Acceptance | 先冻结 COMMIT，再通过 commit_record_ref 绑定 X 回执 | [COMMIT 与回执](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L308-L363) |
| Acceptance → 派发 → 终局 | W 签名派发包承诺原 Action、COMMIT、Acceptance 及 attempt；工具终局、checkpoint 与原请求核验 | [派发包](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L408-L421)；[工具验签](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/tools/common_tool.py#L164-L184)；[终局证据核验](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L473-L500) |

**卖点表述**：从离散消息真实性验证，扩展到同一动作跨阶段的关系一致性验证。

**证据**：[定向篡改验证](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/evaluation/crypto_attack_results.md)；[组合贡献](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/evaluation/core-contributions.md)；[协议 §2–3](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/docs/final/competition-protocol.md#L19-L58)。

**边界**：标准密码学原语不是本作品新发明；贡献在于对象关系、承诺域和生命周期控制的组合。哈希本身不认证来源；需要可信签名或已认证承诺作为验证锚点。

### 4.3 一种统一机制：全生命周期的确定性安全治理（建议绿色）

**问题**：前置审批、资源管理、派发执行、终局验证如果相互独立，可能出现状态竞争、重复派发或证据脱节。

**机制**：以 W 为统一安全核心，按阶段执行确定性检查和持久状态转换，冻结同一动作、资源及证据，并处理未知、失败和恢复。

```text
W 统一安全核心
  ├─ PREPARE：初检与短时准备凭据（非接受）
  ├─ ACCEPT：事务内重核、GoalFloor、预留、COMMIT 与冻结
  ├─ RECEIPT：X 签署原冻结 Core（失败只恢复原回执）
  ├─ CLAIM：重核相应条件，原子固定唯一 attempt
  ├─ EXEC-0：先持久消费执行资格，再向工具派发
  ├─ QUERY：认证查询原 attempt；不重新执行
  └─ SETTLE：可信终局、一次结算、资源与义务状态反馈
```

**卖点表述**：把授权、资源约束、唯一执行资格、恢复和终局证据统一到一个可核验的安全治理机制中。

**源码与证据**：[接受及回执](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L257-L363)；[领取、取消、执行和查询](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L395-L472)；[终局、结算及审计](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/core/common_w.py#L473-L542)；[并发验证](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/evaluation/concurrency_results.md)；[崩溃恢复验证](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/evaluation/crash_recovery_results.md)；[协议 §4–7](https://github.com/yumir3297/Cryptography-Technical-Competition/blob/e9b3cfe92deba1274810d161c561fb8039189044/competition/docs/final/competition-protocol.md#L149-L244)。

**边界**：原子性是各自事务边界的原子性，不是从 Agent 提案到外部工具效果的一个长事务；未知效果保留占用，不能保证生产效果恰好一次或任意跨 Profile 原子性。

## 5. 总体布局与视觉编排

### 5.1 建议的答辩级总体架构

```text
                 人类 / C 受信控制面 / E 来源认证
                            │ 签名约束与来源
                            ↓
         ┌────────────────── 协议安全控制层 ──────────────────┐
Agent ──→│ 可信构造 → 关系核验 → W 原子接受 → 回执 → 唯一资格 │──→ 工具端
候选意图 │                         ↑                      │   │   执行效果
         │                 GoalFloor / 资源及义务账本      │   │
         │                         ↑                      ↓   │
状态反馈←│ 认证状态读取 ← 资源/义务更新 ← 一次结算与终局核验   │←── 签名终局
         └──────────────────────────────────────────────────┘
              ══ 跨阶段密码学证据绑定 / 独立审计 ══
```

布局仅用于说明组件关系，不替代第二节的异常分支和阶段精确语义。C/E 分角色标识，W 状态更新反馈与给 Agent 的认证投影应分开表达；工具响应需先核验，不能直接驱动账本释放。

## 7. 交付验收清单

### 7.1 逻辑正确性（必过）

- [ ] C/W 同库、工具独立账本；准确标注阶段事务边界。
- [ ] PREPARE、ACCEPT 及 CLAIM 的检查范围区分明确。
- [ ] 回执待签只恢复原 Core，不能新领取 attempt。
- [ ] GoalFloor 四类输入、公式、模式及适用范围完整。
- [ ] OPEN/PENDING/DONE/BLOCKED 状态及反馈路径完整，UNKNOWN 保留占用。
- [ ] EXEC-0 持久消费在工具派发之前；QUERY 仅查询原 attempt。
- [ ] CANCEL 不表示任意回滚；可信矛盾与普通未知/无效证据区分。
- [ ] ActionHash、Refs、签名的证据关系与程序控制流区分。
- [ ] C、E、Agent、H/G/U/V/X、W/worker、工具端职责与信任边界正确；主图允许折叠角色但详细图应可追溯。
- [ ] 不把 Server 与 HTTP/MCP 画成串联必经路径。

### 7.2 答辩表达（必过）

- [ ] 三个核心卖点均有独立视觉焦点，并能对应源码及实验依据。
- [ ] 七个步骤可顺着主流程快速读懂，异常不喧宾夺主。
- [ ] 评委能够区分「Agent 提案」和「协议确定性治理」。
- [ ] 公式注明必要资源下界，不夸大为目标可达性证明。
- [ ] 标注标准密码学原语与本协议组合贡献的区别。
- [ ] 不把模拟工具效果说成真实生产设备效果，不把规则消融说成具体竞品同测。
